The one idea

토큰은 만능 열쇠가 아니라, 조건이 적힌 출입증이다.

앱이 받는 access token에는 “어디에, 무엇을, 얼마나 오래” 허용했는지가 묶인다.

정확히 말하면: 토큰의 실제 형식은 구현마다 다르며 앱이 내용을 읽을 수 없는 문자열일 수도 있다. 중요한 것은 권한 서버가 발급하고 리소스 서버가 검증한다는 점이다.

Step-through simulation

PKCE가 code를 한 번 더 잠근다.

앱이 먼저 비밀 난수인 verifier를 만들고, 그 해시인 challenge만 보낸다. 돌아온 code를 누가 훔쳐도 verifier 없이는 토큰으로 바꾸기 어렵다.

준비 · 0 / 5

앱이 일회용 증명을 준비한다.

무작위 verifier는 앱에 보관하고, SHA-256으로 만든 challenge만 권한 요청에 실어 보낸다.

verifier · 앱에 보관 challenge · 보낼 값
  1. 1
    권한 요청 ◆브라우저 → 권한 서버 · challenge 포함
  2. 2
    로그인·동의 후 code 발급권한 서버 → 앱의 정확한 redirect URI
  3. 3

  4. 4

  5. 5
    허용 scope로 API 호출앱 → 리소스 서버 · access_token 포함

+ PKCE S256

PKCE는 모바일·브라우저 앱뿐 아니라 웹 앱을 포함한 모든 종류의 OAuth 클라이언트에 적용되는 현재 보안 권고다.

  • 1
    redirect URI는 미리 등록하고 정확히 비교

    비슷한 주소가 아니라 등록된 주소와 정확히 일치시켜 code가 공격자에게 새지 않게 한다.

  • 2
    필요한 최소 scope만 요청

    사진 읽기만 필요하다면 삭제·업로드 권한까지 받지 않는다.

  • 3
    토큰은 TLS로 보내고 안전하게 보관

    access token은 그 자체가 자격 증명이다. URL에 노출하지 않고 로그에도 남기지 않는다.

  • 4
    로그인이 목적이면 OIDC를 사용

    access token을 사용자 신원 증명서처럼 해석하지 않는다.

왜 예전 방식은 보이지 않나요?
  • Implicit Grant는 access token이 브라우저 URL에 노출될 위험 때문에 현재 보안 권고에서 사용하지 않는 방향이다.
  • Password Grant는 앱이 사용자 비밀번호를 직접 받게 하므로 사용하지 않아야 한다.
  • 정확한 구현은 서비스 유형, 위협 모델, 사용 중인 OAuth 공급자의 문서를 함께 따라야 한다.

확인한 표준

  • RFC 6749 — The OAuth 2.0 Authorization Framework역할, access token, scope, Authorization Code 흐름
  • RFC 7636 — Proof Key for Code Exchange (PKCE)verifier, challenge, token endpoint 검증
  • RFC 9700 — Best Current Practice for OAuth 2.0 Security2025년 보안 권고, PKCE S256, redirect URI, 폐기된 방식
  • OpenID Connect Core 1.0OAuth 위에 인증을 더하는 openid scope와 ID Token

이 페이지는 OAuth 2.0의 사용자 권한 위임을 입문 수준으로 설명한다. 공급자별 endpoint, token 형식, scope 이름, 세션·쿠키 저장 전략은 일반화하지 않았으며 실제 구현에서는 공급자 문서와 위협 모델을 추가로 확인해야 한다.

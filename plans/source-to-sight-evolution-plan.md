## 1. 제품 정의와 범위

### 1.1 한 줄 정의

> **저장소의 실제 코드와 문서를 근거로, 처음 보는 사람도 프로젝트가 무엇이며 어떻게 동작하고 왜 그렇게 판단하는지 이해할 수 있는 오프라인 HTML 설명서를 만드는 스킬.**

- 제품명: Source to Sight.
- 배포 형태: 공개 Agent Skills 형식의 스킬 패키지.
- 실행 환경: 파일 탐색·읽기·출력이 가능한 AI 코딩 에이전트. 특정 CLI나 서브에이전트 기능에 종속하지 않는다.
- 핵심 사용자: 프로젝트에 처음 합류한 개발자, 다른 분야의 개발자, 해당 코드의 배경지식이 없는 협업자.
- 성공 기준: 소스 코드를 읽지 않고도 **목적, 입력과 결과, 주요 구성, 핵심 동작, 조건과 한계**를 자기 말로 설명할 수 있다.

### 1.2 범용성은 필수 요구사항

**웹은 여러 적용 사례 중 하나다.** 프로젝트를 Controller → Service → Repository → DB 형태로 맞추지 않는다. 서버·라우트·데이터베이스가 없어도 같은 제품으로 설명할 수 있어야 한다.

| 프로젝트 유형 | 설명할 질문의 예 | 실제 코드에서 확인할 단서 |
| :--- | :--- | :--- |
| 웹 서비스·웹 앱 | 요청이나 사용자 조작이 어떤 결과를 만드는가? | 라우트, 화면 이벤트, 상태 변경, 서버 호출, 저장 처리 |
| CLI·유틸리티 | 명령이나 입력 파일이 어떤 과정을 거쳐 결과로 바뀌는가? | 명령 등록, 인자·설정 처리, 변환 함수, 표준 입출력, 파일 생성 |
| 라이브러리·SDK | 사용자는 무엇을 호출하고 어떤 약속을 따라야 하는가? | 공개 API, 내보내기, 타입, 예제·테스트, 반환값, 오류 계약 |
| 프레임워크·플러그인 시스템 | 초기화·등록·콜백·종료는 누가 어떤 순서로 수행하는가? | 부트스트랩, 레지스트리, 확장 지점, 디스패치, 훅, 생명주기 |
| AI 에이전트·하네스 | 모델·도구·상태가 어떻게 협력하고 언제 반복을 끝내는가? | 실행 루프, 모델 호출, 도구 등록·실행, 상태·메모리, 위임, 종료 조건 |
| 데이터·이벤트·백그라운드 처리 | 데이터나 이벤트가 어떤 단계와 상태를 거치는가? | 작업 그래프, 변환 단계, 스케줄, 발행·소비, 체크포인트, 재처리 |

이 목록은 초기 검증 축이다. 데스크톱 앱, 빌드 도구, 게임 엔진, 시스템 도구 등도 **실제 근거로 해소 가능한 범위**에서 같은 모델을 적용한다. 모든 언어·프레임워크를 완전 분석한다고 약속하지 않는다. 검증한 유형과 탐색하지 못한 범위를 명시한다.

모노레포나 혼합 프로젝트는 여러 유형을 함께 가질 수 있다. 예를 들어 에이전트 서버는 웹 요청 처리, 에이전트 반복, 도구 라이브러리를 함께 설명할 수 있다. 저장소 전체를 한 유형으로 강제 분류하지 않는다.

### 1.3 만드는 것과 책임 범위

주요 엔지니어링 산출물은 다음과 같다.

1. **공통 설명 데이터 모델(Understanding Graph IR):** 구조, 동작, 시나리오, 상태 변화, 규칙과 근거를 표현한다.
2. **고정 렌더러:** 데이터에 따라 그래프·설명 패널·경고·선택적 재생을 표시한다. HTML 안에 스타일과 스크립트를 포함한다.
3. **탐색·해설·조립 계약:** 사실과 설명을 분리하고 검증 결과를 일관되게 전달한다.
4. **프로젝트별 탐색 지침:** 해당 프로젝트에서 실제 관계를 찾는 방법을 안내한다.
5. **여러 유형의 평가 케이스:** 정확성과 이해 가능성을 지속적으로 검증한다.

언어별 컴파일러·AST 파서, 프로그램 실행 하네스, 범용 정적 분석기를 새로 만드는 것은 현재 개발 범위에 넣지 않는다. 호스트가 제공하는 코드 탐색 능력을 활용하되, **AI 에이전트 하네스 자체는 분석 대상에 포함한다.** 분석 대상 프로그램을 자동 실행하거나 외부 모델·서비스를 호출하는 기능도 전제하지 않는다.

### 1.4 하나의 제품, 세 단계의 설명

| 계층 | 스킬 | 대상과 질문 | 화면 |
| :--- | :--- | :--- | :--- |
| ① 프로젝트 지도 | `codebase-atlas` | 저장소/패키지의 목적, 구성, 주요 기능과 확장 지점은 무엇인가? | 공통 탐색 UI를 가진 고정 템플릿 |
| ② 동작과 협력 | `code-flow` | 선택한 기능·사용 사례·생명주기는 어떻게 작동하고 무엇이 협력하는가? | 관계와 필요 시 시간 순서를 보여주는 고정 템플릿 |
| ③ 규칙과 이유 | `visual-primer` | 같은 대상은 어떤 조건·계약·판단 규칙을 따르는가? | 주제에 맞게 구성하는 자유 형식 설명 페이지 |

**②와 ③의 공통 단위는 “범위가 정해진 설명 대상”이다.** 하나의 HTTP 진입점으로 제한하지 않는다.

- 웹: 주문 생성 요청 / 화면 검색 동작.
- 유틸리티: 파일 변환 명령 / 문자열 정규화 함수.
- 라이브러리: 클라이언트 생성부터 자원 해제까지의 사용 사례.
- 프레임워크: 플러그인 등록부터 콜백 실행까지의 생명주기.
- 에이전트: 요청 수신부터 도구 반복과 최종 응답까지의 한 실행.
- 데이터 처리: 입력 데이터가 결과 파일로 변환되는 작업.

생명주기는 여러 훅을 포함할 수 있다. 라이브러리는 실행 파일이 없어도 공개 함수와 사용 예제에서 시작할 수 있다. 구조적 관계에는 실행 순서를 억지로 붙이지 않는다.

사용자는 어느 계층에서나 시작할 수 있고, 필요한 설명만 생성한다. ②와 ③을 함께 생성하면 같은 대상·범위·스냅샷을 공유한다. 기존 `visual-primer`의 일반 개념 설명 기능도 유지한다. 일반 개념 설명은 저장소 분석과 구분하고 자료 출처를 명시한다.

①②는 탐색 방식과 근거의 위치를 일관되게 유지한다. ③은 조건 비교, 입력/결과 예시, 상태 변화 등 대상에 맞는 표현을 선택하되 사실 계약은 공유한다.

### 1.5 불변 원칙: 코드를 읽지 않아도 이해한다

- **결과 HTML 어디에도 소스 코드 본문을 넣지 않는다.** 화면, 접힘 영역, 숨겨진 DOM, 데이터 스크립트에도 스니펫·발췌 코드·원문 프롬프트를 넣지 않는다.
- 제목과 설명은 쉬운 말로 작성한다. 클래스·함수·도구·테이블 이름은 보조 표기로만 사용한다.
- 파일 경로·심볼명·라인 범위는 근거의 위치로 표시할 수 있다.
- 기술 개념은 필요할 때 짧게 풀어 쓴다. 웹의 업무 용어가 없는 프로젝트에는 기능·사용자 관점의 표현을 쓴다.
- 실제 관찰하지 않은 실행 결과, 모델의 내부 추론, 동적으로 선택될 경로를 확정 사실로 표현하지 않는다.
- 문서에 소스 코드가 없어도 파일 경로와 식별자는 내부 구조 정보다. README에 이 범위를 안내한다.

현재 `skills/visual-primer/SKILL.md`에는 코드를 후반부나 접힘 영역에 배치할 수 있는 지침이 있다. **M0에서 이 원칙과 충돌하는 지침을 정리한다.**

### 1.6 범용성의 완료 기준

다음 조건을 모두 통과해야 “범용 코어”로 인정한다.

1. HTTP·서버·DB가 없는 저장소도 정상 결과를 만든다.
2. 프로젝트 유형을 바꾸어도 렌더러에 프레임워크별 조건문을 추가하지 않는다.
3. 노드 하나인 유틸리티와 실행 순서가 없는 관계 설명도 실패로 취급하지 않는다.
4. 프레임워크의 역방향 제어와 에이전트의 반복·불확실성을 사실에 맞게 표현한다.
5. 처음 보는 독자가 설명할 수 있는지 여러 프로젝트 유형에서 확인한다.

## 2. 공통 분석 파이프라인과 탐색 지침

### 2.1 처리 단계

~~~text
프로젝트 맥락·설명 대상 식별
  → 1. 탐색: 사실·근거·미해소 지점
  → 2. 해설: 쉬운 설명·선택적 시나리오
  → 3. 조립·검증: IR·근거 위치와 내용·표시 범위
  → 렌더링·출력
~~~

**0. 프로젝트 맥락·대상 식별**

- README, 빌드·패키지 설정, 디렉터리, 공개 API, 실행·등록 지점, 예제·테스트를 필요한 범위에서 읽는다.
- 언어·프레임워크 이름만으로 구조를 결정하지 않는다. 실제 책임과 관계를 찾는다.
- 사용자가 알고 싶은 질문, 대상 심볼/설정/등록 지점, 시작과 끝, 포함·제외 범위를 정한다.
- 관련 탐색 지침을 선택한다. 여러 지침을 조합할 수 있다.

**1. 탐색(Fact-Finder)**

- 물리적 연결과 동작 규칙을 실제 코드·설정·문서에서 추적한다.
- 산출물: 노드·관계·상태·규칙 후보, 각 주장의 근거, 탐색 범위, 미해소 후보.
- 모호한 관계는 확정하지 않는다. 라이브러리 공개 API와 내부 구현, 프레임워크 호출자와 콜백, 에이전트 제어 루프와 모델 응답을 구분한다.
- 문서가 설명하는 계약과 구현의 현재 동작이 다르면 양쪽 위치와 차이를 기록한다.

**2. 해설(Explainer)**

- 역할 설명은 1~3문장으로 작성하고 입력·처리·결과와 중요한 제한을 설명한다.
- 시간 순서가 있는 대상만 시나리오 스텝으로 구성한다.
- 탐색 결과에 없는 컴포넌트, 관계, 조건, 숫자를 새로 만들지 않는다.
- 해설에 필요한 사실이 부족하면 탐색 단계로 되돌린다.

**3. 조립·검증(Assembler)**

- IR 조립 → 구조 검증 → ID 참조 검증 → 근거 위치·내용 검증 → 표시 예산 적용 → 경고 집계.
- 검증하지 못한 범위를 사용자에게 보이는 상태로 남긴다.
- 검증 전용 자료를 제거한 출력용 데이터만 템플릿에 주입한다.

### 2.2 호스트 독립성

`SKILL.md`는 단계별 입력·출력과 금지 사항을 규정한다. 실행 형태는 호스트가 정한다. 동일 컨텍스트에서 순차 실행해도 계약은 같다. 서브에이전트는 호스트가 제공하고 사용을 허용할 때만 선택적으로 이용한다.

지침에는 “파일 검색 도구”, “파일 읽기 도구”, “브라우저 확인 도구”처럼 능력을 적는다. 특정 호스트의 도구 이름이나 특정 모델의 사용을 필수로 만들지 않는다.

### 2.3 입력과 대상 해소

| 입력 | 예시 | 해소 방식 |
| :--- | :--- | :--- |
| 자연어 질문 | “이 변환 도구가 파일을 처리하는 과정을 설명해 줘” | 관련 기능과 실제 실행/공개 지점 탐색 |
| 심볼·공개 API | `normalize`, `Client.connect` | 선언·호출·사용 계약 확인 |
| 파일:라인 | `src/runner.ts:80` | 해당 동작과 포함 범위 확인 |
| 명령·라우트·이벤트 | `convert --format png`, `POST /orders`, `job.completed` | 등록·디스패치·처리 지점 확인 |
| 사용 사례·생명주기 | “플러그인이 등록되어 실행되기까지” | 하나의 범위 안에서 여러 훅·단계 해소 |
| 저장소·패키지 | “이 라이브러리 전체 구성을 설명해 줘” | ① 지도에서 주요 기능과 관계 탐색 |

하나의 대상이 명확하면 진행한다. 시작점이 여러 개라도 **같은 생명주기의 구성 요소로 확인된 경우** 하나의 설명 대상에 포함할 수 있다. 서로 다른 후보가 남거나 대상을 찾지 못하면 검색 범위와 후보의 파일:라인을 제시하고 되묻는다. 조용히 임의의 대상을 선택하지 않는다.

### 2.4 공통 코어와 탐색 프로파일 분리

**프로파일은 탐색 방법을 적은 문서다.** 별도 분석 엔진이나 실행 플러그인 프레임워크를 만들지 않는다.

공통 지침은 심볼·호출·등록·상태·공개 계약·경계·근거 검증을 다룬다. 프로젝트별 지침은 “무엇을 어디서 찾아야 하는가”만 보충하고 같은 IR을 출력한다.

| 프로파일 | 찾아야 할 관계 | 오해를 막는 규칙 |
| :--- | :--- | :--- |
| `web` | 요청/화면 이벤트, 핸들러, 상태·외부 호출 | REST와 계층형 서버 구조를 강제하지 않음 |
| `cli-utility` | 명령, 옵션·설정 우선순위, 변환, 입출력 | 작은 함수에 가상의 계층·저장소를 추가하지 않음 |
| `library-sdk` | 공개 API, 사용 순서, 오류·자원 계약 | 공개 기능과 내부 보조 구현을 구분 |
| `framework-plugin` | 등록, 확장 지점, 디스패치, 생명주기 | 등록됐다는 사실만으로 실행 순서·실제 호출을 확정하지 않음 |
| `ai-agent` | 모델/도구 호출, 루프, 상태·메모리, 위임, 종료 | 모델 출력에 따른 후보 경로와 코드로 정해진 제어를 구분 |
| `data-event` | 작업 그래프, 변환, 발행·소비, 체크포인트 | 동일 이벤트 이름만으로 소비자·순서·전달 보장을 확정하지 않음 |

필요하면 언어·프레임워크별 보조 지침을 추가한다. 예: Python 패키지 공개 API, JavaScript 플러그인 등록, Spring 라우팅·영속성·이벤트. **Spring은 이 보조 지침 중 하나다.** 새 프로파일은 기존 검증과 렌더링 규칙을 우회할 수 없다.

### 2.5 출력 언어와 경로

- 기본 언어는 사용자가 질문한 언어다. 명시한 언어가 있으면 그 언어들만 생성한다.
- 여러 언어를 요청하면 파일을 언어별로 분리한다. 코드상의 이름과 파일 경로는 원문을 유지한다.
- 기본 경로: 지도는 `docs/atlas.html`, 동작 설명은 `docs/flows/<subject-key>.html`, 규칙 설명은 `docs/flows/<subject-key>-logic.html`.
- `subject-key`는 HTTP 메서드가 필수가 아닌 안정적인 대상 키다. 패키지·정규화된 대상·범위로 구분하고 충돌 시 짧은 식별자를 붙인다. 같은 이름의 다른 모듈/오버로드를 덮어쓰지 않는다.
- 다국어 파일은 `<subject-key>-ko.html`, `<subject-key>-logic-en.html`처럼 구분한다. 사용자가 지정한 경로가 우선이다.

## 3. 신뢰 모델과 설명의 정확성

### 3.1 근거의 종류와 확인 상태를 구분한다

| `confidence` | 뜻 | 기본 표현 |
| :--- | :--- | :--- |
| `exact` | 직접 호출·명시적 설정·대입 등으로 확인한 주장 | 검증 통과 시 실선/확인 표시 |
| `resolved` | 등록·타입·프레임워크 규칙과 실제 연결 근거를 함께 확인한 주장 | 검증 통과 시 실선 + 해석 근거 표시 |
| `inferred` | 근거가 있으나 하나로 확정하지 못한 후보 | 점선/추정 표시 |

이 분류와 별도로 **근거 위치가 일치하는지**, **그 근거가 실제 주장을 뒷받침하는지**를 기록한다. 근거 파일이 없다는 이유로 `exact`를 `resolved`로 바꾸지 않는다. `resolved`에는 해석 규칙과 그 규칙이 적용된 증거가 필요하기 때문이다.

노드·엣지·시나리오 스텝·상태 전이·규칙에 같은 검증 정책을 적용한다. 미확인 주장은 원래 분류와 관계없이 화면에서 확정 표시를 받을 수 없다.

### 3.2 탐색의 불변 규칙

1. 실제 컴포넌트·관계·상태·규칙 주장에는 파일·심볼/설정 키·라인 범위의 근거를 연결한다.
2. 사용자, 호출 환경 같은 **설명을 위한 문맥 노드**는 `contextOnly: true`로 구분한다. 근거가 없으면 신뢰도·검증 완료 표시를 붙이지 않는다. 이 예외로 실제 구현 노드를 무근거로 만들 수 없다.
3. 문맥 노드와 실제 구현 사이의 화살표에는 코드에서 확인한 진입/사용 계약 근거가 필요하다. 확인하지 못하면 연결하지 않는다.
4. 저장소 밖 시스템과 동적 코드는 경계로 표시하고 내부 동작을 추정하지 않는다.
5. 확정하지 못한 후보는 점선과 후보 설명 또는 경고로 남긴다. 가능한 여러 콜백·구현체를 임의로 하나 고르지 않는다.
6. 숫자, 단위, 기본값, 설정 재정의, 재시도 횟수, 종료 조건은 실제 적용 범위까지 확인한다.
7. 테스트·예제는 사용 사례의 근거가 될 수 있지만, 이름만 읽고 구현이나 모든 환경의 보장으로 일반화하지 않는다.

### 3.3 근거 재검증: 위치와 내용의 두 단계

**A. 위치 검증 — 기계적으로 확인 가능한 부분**

- 실제 파일을 다시 읽고 라인 범위가 유효한지 확인한다.
- 검증 전용 `anchorText`가 해당 범위에 존재하는지 검사한다.
- 파일 내용 해시와 스냅샷을 기록한다. 선언부가 그대로여도 본문이 바뀌면 재검증 대상이다.
- 결과를 `locationStatus: passed | failed`로 기록한다. 이 상태는 의미가 맞다는 인증이 아니다.

**B. 내용 검증 — 주장이 근거에서 도출되는지 다시 읽고 확인**

- 호출 엣지는 호출 위치와 대상 해소 근거를 확인한다. 함수 선언부만으로 호출 관계를 증명하지 않는다.
- 등록·콜백은 등록 위치, 디스패치 규칙, 대상 연결을 확인한다.
- 상태 변화와 규칙은 실제 조건·대입·분기와 해당 경로를 확인한다.
- 수치 규칙은 값·단위·비교 조건·설정 우선순위까지 확인한다. “재시도 3회”와 “총 시도 3회”를 구분한다.
- 결과를 주장별 `supportStatus: supported | uncertain | unsupported`로 기록하고, 짧은 쉬운 말의 확인 사유를 남긴다.
- 에이전트의 재독해는 완전한 증명이 아니다. 사람의 표본 검증과 골든셋 평가로 오류를 측정한다.

**표시 정책**

- `exact/resolved` + 위치 통과 + 내용 뒷받침이 모두 충족되어야 확정 표시한다.
- `inferred` 또는 `uncertain`은 불확실성을 표시하고 핵심 결론의 확정 근거로 사용하지 않는다.
- `unsupported` 주장은 확정 그래프·시나리오·규칙 본문에서 제외하고 검토 경고로 이동한다. 참조가 끊긴 시나리오는 수정하거나 제외한다.
- 파일 불일치는 `evidence-unverified` 경고와 상단 요약에 반영한다.
- **숫자·임계값을 포함한 규칙은 위치와 내용 검증을 모두 통과하지 못하면 설명 본문에 싣지 않는다.**

`anchorText`와 검토용 코드 자료는 검증 전용이다. 출력용 IR에 포함할 수 없도록 별도 스키마로 검증하고 HTML 전체에서 제거 여부를 확인한다.

### 3.4 정적 분석의 한계를 정확히 설명한다

- 정적으로 확인한 흐름은 “가능한 동작/코드에 정의된 동작”이다. 실제 실행 기록처럼 표현하지 않는다.
- AI 에이전트의 모델 응답, 도구 선택, 위임 결과는 코드에 고정되지 않을 수 있다. 확인한 후보·검사·반복·종료 규칙만 설명한다.
- 런타임 플러그인 로딩이나 외부 설정이 필요하면 미해소 지점과 추가로 필요한 자료를 표시한다.
- 외부 문서를 참조해야 하면 해당 버전과 출처를 기록한다. 구현과 다른 버전의 규칙으로 관계를 확정하지 않는다. 외부 문서는 해석을 돕는 자료이며 저장소의 실제 연결 근거를 대신하지 않는다.
- 런타임 관측 등급과 실행 자동화는 별도 수요·설계가 생길 때 검토한다. 현재 필수 요소로 넣지 않는다.

### 3.5 읽기 쉬운 크기와 사실 보존

핵심 화면은 대체로 5~7개 노드를 목표로 하되 최소 개수를 강제하지 않는다.

1. 보조 변환·헬퍼는 상위 노드의 `actions`에 쉬운 설명과 근거로 흡수한다.
2. 핵심 이해를 방해하는 세부 사항은 `importance: detail`로 두고 상세 보기에서 표시한다.
3. 압축 후 핵심 노드가 7개를 넘으면 경고와 함께 모두 제공한다. 임의로 잘라내지 않는다.
4. 숨긴 노드를 건너뛴 새 호출 엣지를 만들지 않는다. 요약 경로가 필요하면 원래 엣지 목록을 보존하고 “여러 단계 요약”으로 구분한다.
5. 시나리오가 상세 노드를 참조하면 해당 스텝에서 노드를 드러내거나 상세 보기를 안내한다. 사라진 대상을 하이라이트하지 않는다.

작은 함수의 노드 하나, 초기화 훅 두 개, 시나리오 없는 공개 API 관계도 모두 유효한 설명일 수 있다. 접히는 복합 그룹 노드는 기본 렌더러가 검증된 뒤 별도 버전에서 검토한다.

## 4. 화면과 탐색 경험

### 4.1 공통 화면 구성

- **목적과 결과:** 무엇을 위한 기능이며 입력과 결과가 무엇인지 먼저 설명한다.
- **그림:** 핵심 구성과 관계를 보여 준다. 기술적 분류보다 역할을 쉽게 읽을 수 있게 한다.
- **선택 패널:** 이 부분의 역할, 이 대상에서 하는 일, 입력/결과, 상태 변화, 근거 위치를 제공한다.
- **선택적 시나리오:** 순서가 의미 있을 때 이전/다음/자동 재생을 제공한다. 단순 관계 설명에는 재생 UI를 노출하지 않는다.
- **한계와 경고:** 확정하지 못한 관계, 탐색 범위, 외부 경계를 구체적으로 알려 준다.
- **더 알아보기:** 관련 지도·동작·규칙 설명으로 이동한다.

주요 필드는 쉬운 말의 `label`이며 `codeName`은 작게 표시한다. 호출 메서드뿐 아니라 변환·등록·도구 실행 등도 `actions[].plainText`로 설명한다. DB 테이블은 실제 존재하고 대상 이해에 필요한 경우에만 표시한다.

### 4.2 레이아웃 요구사항

M0부터 다음 형태를 다룬다.

- 선형 변환, 분기, 합류, 병렬 fan-out/fan-in.
- 반복과 루프백, 프레임워크의 콜백·역방향 호출.
- 연결되지 않은 공개 기능과 외부 경계.
- 순서가 없는 의존·등록·사용 관계.
- 노드 하나인 유틸리티와 여러 모듈이 협력하는 큰 사례.

노드 겹침, 노드를 관통하는 엣지, 잘못된 화살표 방향은 허용하지 않는다. 교차는 줄이고 혼동되지 않게 처리하되 모든 그래프에서 교차 0건을 요구하지 않는다. 핵심/상세 전환 시 배치가 재계산되어야 한다.

공통 UI 안에서 관계 중심과 순서 중심 배치를 선택할 수 있다. 프로젝트마다 전용 화면이나 프레임워크별 렌더러를 만들지 않는다.

### 4.3 정상·부분 결과·설명 불가

| `analysis.status` | 판단 기준 | 화면 |
| :--- | :--- | :--- |
| `complete` | 명시한 범위의 설명에 필요한 근거가 확보됨 | 정상 설명. 저장소 전체의 완전 분석이라는 뜻은 아님 |
| `partial` | 일부는 설명 가능하지만 중요한 미해소 지점이 남음 | 확인한 그림 + 눈에 띄는 한계·후보 |
| `insufficient` | 요청한 질문에 답할 최소 근거가 부족함 | 추적하지 못한 이유 + 탐색 범위 + 다음 시도 |

**노드 수와 시나리오 유무로 실패를 판정하지 않는다.** 불확실한 핵심 관계가 많으면 경고를 접힌 패널 안에만 숨기지 않는다.

### 4.4 스냅샷과 재생성

헤더에 저장소/패키지, 브랜치·커밋(확인 가능한 경우), 생성 시각, 설명 범위를 표시한다. 미커밋 변경이 있으면 지속적인 표시를 둔다. Git이 없는 디렉터리도 분석할 수 있으며 커밋을 추정해서 채우지 않는다.

출력용 메타데이터에 대상 키, 원래 질문, 범위, 프로파일, 출력 언어, 스키마 버전을 저장하고 짧은 `s2s:regen` 주석을 넣는다. HTTP 라우트만으로 재생성 대상을 식별하지 않는다.

호출 예: `$code-flow --refresh docs/flows/plugin-startup.html`.

재생성 시 대상을 다시 해소하고 변경된 근거를 재검증한다. 찾지 못하면 기존 설명을 새 스냅샷의 확정 결과로 재사용하지 않는다. 원래 질문에도 코드 발췌나 민감한 값이 있으면 그대로 HTML에 복제하지 않는다.

### 4.5 지연 생성과 계층 간 링크

세 계층은 각각 독립된 오프라인 HTML이며 상대경로로 연결한다.

~~~text
docs/
├── atlas.html
└── flows/
    ├── plugin-startup.html
    ├── plugin-startup-logic.html
    └── agent-run.html
~~~

- 대상 파일이 이미 있으면 활성 링크를 표시한다.
- 없으면 설명을 생성할 명령과 복사 버튼을 표시한다. 페이지가 모델을 직접 호출하거나 파일을 자동 생성한다고 안내하지 않는다.
- 파일 존재 여부는 생성 단계에서 확인해 굽는다. 일반적인 `file://` 결과물이 파일 목록을 조회하는 기능에 의존하지 않는다.
- 하위 설명 생성 뒤에는 상위 페이지를 `--refresh`해야 링크 상태가 바뀐다는 안내를 제공한다.
- ①↔②, ②↔③ 이동을 지원한다. ②③은 대상 키·범위·언어와 스냅샷을 비교하고 차이가 있으면 오래된 짝임을 표시한다.

스냅샷 비교는 분석 대상 소스의 커밋·내용 해시를 기준으로 한다. 두 페이지의 생성 시각이나 생성 모델이 다르다는 이유만으로 소스가 달라졌다고 판정하지 않는다.

### 4.6 오프라인과 접근성

HTML 하나가 빌드·서버·외부 요청 없이 동작해야 한다. CSS, 스크립트, 필요한 자산을 포함하고 외부 CDN·폰트에 의존하지 않는다.

UTF-8, 반응형 레이아웃, 키보드 포커스, 색 외의 구분, 그림의 텍스트 대안을 M0부터 제공한다. 모션을 넣을 때부터 `prefers-reduced-motion`을 반영한다. M4는 기본 접근성을 미루는 단계가 아니라 단축키·배속·모바일 조작을 더 다듬는 단계다.

## 5. 데이터 계약: Understanding Graph IR

### 5.1 기술 중립적인 공통 모델

초기 구현 버전은 `0.1.0`으로 시작한다. M0에서는 초안이며 M1.5 베이스라인 이후 동결한다. 이후 변경은 버전을 올리고 회귀 평가한다. 문서에 있는 예시를 그대로 확정 스키마로 간주하지 않고 아래 요구를 실제 JSON Schema와 의미 검증기로 구현한다.

| 영역 | 필드와 책임 |
| :--- | :--- |
| 버전·계층 | `schemaVersion`, `layer`의 값은 `atlas`, `behavior`, `logic` |
| 스냅샷 | `snapshot`: 저장소 식별, 브랜치·커밋·변경 여부, 생성 시각, 스킬 버전, 확인 가능한 모델 정보 |
| 설명 대상 | `subject`: 안정적인 `id`, `kind`, 쉬운 제목, 사용자 질문, 패키지/모듈, 실제 대상 목록 `targets[]`, 포함·제외 범위 |
| 분석 상태 | `analysis`: 상태, 적용한 프로파일, 탐색한 경로/대상, 미해소 사항, 다음 시도 |
| 이야기 | `summary`: 목적, 입력, 결과, 핵심 설명, 중요한 제한 |
| 구성 | `nodes[]`: 역할, 쉬운 이름, 실제 이름, 요약, 핵심/상세, 수행 동작, 근거와 주장 검증 |
| 관계 | `edges[]`: 출발·도착 ID, 관계 의미, 쉬운 설명, 도출 방법, 근거와 주장 검증 |
| 순서 | `scenarios[]`: 선택적인 사용/동작 순서, 조건, 반환 설명 |
| 상태 | `stateTransitions[]`: 대상 노드, 전후 상태의 쉬운 이름, 트리거, 근거와 주장 검증 |
| 규칙 | `rules[]`: 조건, 결과, 설명, 근거와 주장 검증. M3에서 자동 생성 범위를 확대 |
| 근거·한계 | `evidence[]`, `warnings[]`, 보조 외부 출처 `sources[]` |
| 이동·재생성 | `links`: 지도·동작·규칙 링크 상태와 생성 명령, `regeneration`: 재생성에 필요한 대상·범위·언어 |

`subject.kind`는 다음의 닫힌 집합으로 시작한다.

~~~text
project       저장소/패키지 전체
capability    공개 기능·함수·명령·요청·화면 동작
workflow      여러 단계가 협력하는 사용 사례·작업·에이전트 실행
lifecycle     생성·등록·초기화·호출·종료의 생명주기
~~~

HTTP 메서드·라우트, 명령 이름, 이벤트 이름, 공개 심볼 등은 해당할 때만 `targets[]`에 기록한다. HTTP 필드는 필수가 아니다. 프로파일은 탐색에만 사용하며 렌더러 동작의 분기 키로 쓰지 않는다.

### 5.2 노드·관계·시나리오

~~~text
node.kind       actor | component | state | artifact | boundary
node.importance core | detail
edge.type       invokes | passes-data | depends-on | registers | dispatches
                | reads | writes | emits | consumes | transitions | delegates
edge.derivation direct-code | explicit-config | symbol-resolution
                | registration-rule | framework-rule
                | documentation | test-example | pattern
confidence      exact | resolved | inferred
scenario.kind   typical | alternate | error | retry | lifecycle
step.branch     normal | alternate | error | retry | stop       (선택 항목)
~~~

위 `step.branch`는 선택 항목이다. 닫힌 열거형은 의미와 표현을 정한다. 프레임워크별 이름은 별도 `roleLabel`·`codeName`으로 표시하고 열거형에 계속 추가하지 않는다.

| 사례 | 공통 모델로 표현하는 방법 |
| :--- | :--- |
| CLI 파일 변환 | 명령 처리 `component` → 입력 `artifact` 읽기 → 변환 `component` → 출력 `artifact` 쓰기 |
| 라이브러리 함수 하나 | `capability` 대상과 `component` 노드 하나, 입력·결과·규칙. 엣지와 시나리오는 없어도 유효 |
| 프레임워크 플러그인 | 등록자와 확장 구현의 `registers`, 디스패처에서 구현으로 `dispatches`, 생명주기 시나리오 |
| 에이전트 실행 | 실행기 `component`, 대화 상태 `state`, 외부 모델 `boundary`, 도구 실행 `component`, 호출·상태 갱신·반복 |
| 웹·데이터 처리 | 실제 구현에 따라 처리 `component`, 저장 상태 `state`, 메시지/파일 `artifact`, 외부 시스템 `boundary` |

추가 규칙:

- `nodes[].actions[]`는 `id, plainText, codeName?, evidenceIds, confidence, supportStatus`를 가진다. 메서드 목록으로 제한하지 않는다.
- 시나리오 스텝은 `edgeId`와 `nodeId` 중 정확히 하나를 참조한다. 캡션·조건·반환값도 사실 주장으로 검증한다.
- 응답은 필요한 경우 `step.returns`로 설명한다. 반환을 표현하기 위해 가상의 역방향 호출 엣지를 추가하지 않는다.
- 구조적 관계와 실행 순서를 구분한다. 등록·의존 엣지를 자동으로 실행 스텝으로 바꾸지 않는다.
- 상태 전이는 `subjectNodeId`로 실제 대상에 연결한다. 문자열 이름을 맞춰 패널에 임의 배치하지 않는다.
- 문맥 노드에는 `contextOnly: true`를 사용하고, 신뢰도·주장 검증 필드를 생략하는 조건부 스키마를 둔다.
- 링크 대상 상태는 `{ url, generated, command? }`로 표현한다. `generated: false`이면 생성 명령이 필요하다.

① 지도는 같은 노드·관계·근거 계약을 재사용한다. 추가로 구역 소속과 설명 가능한 대상 목록이 필요하다. M0에서 최소 지도 픽스처로 계약을 검토하고 M5에서 실제 탐색을 구현한다. 구역은 접히는 복합 실행 노드와 구분한다.

### 5.3 검증용 IR과 출력용 IR

검증용 근거:

~~~text
id, kind(code/config/documentation/test), file, symbolOrKey,
startLine, endLine, anchorText, contentHash, locationStatus
~~~

주장별 검증:

~~~text
confidence, evidenceIds, supportStatus, verificationNote
~~~

- 검증용 IR에는 위치 확인용 `anchorText`가 필요하다.
- 출력용 IR은 허용 필드만 새로 조립한다. `anchorText`, 코드 원문, 원문 프롬프트, 내부 검토용 발췌를 허용하지 않는다.
- `verificationNote`는 근거가 무엇을 뒷받침하는지 쉬운 말로 요약한다. 원문 인용을 저장하는 통로로 쓰지 않는다.
- 외부 출처는 `sources[]`에 URL·제목·대상 버전·조회 시점을 기록하고, 필요 시 `sourceIds`로 연결한다. 실제 구현 주장은 별도의 저장소 `evidenceIds`를 가져야 하며 외부 출처만으로 위치 검증을 통과시킬 수 없다.
- 출력 그래프에 남는 주장은 `supported` 또는 불확실성을 드러낸 `uncertain`이어야 한다. `unsupported`는 경고로 이동한다.
- `rules[]`는 M0에서 소규모 계약 픽스처로 검증하되 본격적인 규칙 탐색·페이지 생성은 M3 범위다. 업무 규칙 외에도 API 계약, 옵션 우선순위, 생명주기, 도구·종료 규칙을 담는다.

### 5.4 구조 검사와 의미 검사를 분리한다

JSON Schema는 필수 필드, 타입, 열거형, 조건부 필드, 스텝의 택일 규칙, 출력용 금지 필드를 검사한다.

별도 의미 검증기는 다음을 검사한다.

- ID 중복과 모든 노드·엣지·스텝·상태·근거·외부 출처 참조의 존재.
- 실제 주장에 근거가 연결되는지, 문맥 노드 예외가 적법한지.
- 위치·내용 검증 결과와 화면의 확정 표시가 일치하는지.
- 제외한 주장 때문에 시나리오·상태·경고 참조가 끊기지 않는지. 제외한 주장의 설명은 경고의 후보 정보에 남기고 유효하지 않은 ID를 참조하지 않는다.
- 범위·대상·언어·스냅샷이 짝 페이지와 맞는지.
- 시나리오가 없거나 노드가 적다는 이유로 유효 데이터를 거부하지 않는지.

JSON Schema의 `$ref`와 데이터 내부 ID 참조는 별개의 검사다. 새 프로파일이 정의되지 않은 값을 쓰면 조용히 임의 스타일로 그리지 않고 구체적인 검증 오류를 반환한다.

### 5.5 경고와 안전한 출력

`warning.severity`는 `high | medium | low`이고 초기 `warning.kind`는 다음과 같다.

~~~text
subject-ambiguous | ambiguous-target | unresolved-dispatch
evidence-unverified | claim-unsupported | dynamic-behavior
external-boundary | node-budget-exceeded | coverage-limited | snapshot-mismatch
~~~

경고에는 쉬운 설명, 실제로 유효한 관련 ID, 후보 위치, 필요 시 다음 시도를 담는다. 내부 스택 트레이스나 구현 상세를 사용자의 주된 설명에 노출하지 않는다.

주입 시 JSON과 텍스트를 각 문맥에 맞게 이스케이프한다. 라벨·파일명에 따옴표·HTML 종료 태그가 있어도 문서가 깨지거나 데이터가 실행되지 않아야 한다. 재생성 주석과 링크도 같은 기준으로 검증한다.

## 7. 개발 단계와 완료 기준

### 7.0 진행 원칙

1. **범용성·정확성·이해 가능성을 먼저 검증한다.** 웹 기능 완성 후 다른 프로젝트를 끼워 맞추는 순서로 진행하지 않는다.
2. 각 마일스톤은 게이트다. 완료 기준을 충족하지 못하면 미충족 항목을 남기고 다음 단계 완료를 주장하지 않는다.
3. M0부터 실제 저장소에서 추적한 비웹 사례를 사용한다. 손으로 만든 이상적인 데이터만으로 통과시키지 않는다.
4. 웹에서 쓰이는 레이어·저장소·테이블·HTTP 필드를 다른 유형의 필수 값으로 만들지 않는다.
5. 일반 개념 설명과 저장소 근거 설명의 차이는 유지하되, 쉬운 말·코드 비노출·오프라인이라는 제품 원칙은 공유한다.
6. 사람 검토가 필요한 항목은 실제 검토 기록으로 완료한다. 에이전트의 자체 확인을 사람 검토로 대체해 표기하지 않는다.

~~~text
M0 ──▶ M1 ──▶ M1.5 ──▶ M2 ──▶ M3 ──▶ M4 ──▶ M5
공통    범용    유형별    복합     규칙     사용성    프로젝트
계약·UI 동작    골든셋    동작     해설     개선      지도
~~~

②의 근거와 설명 계약을 먼저 만들고 ③과 ①을 완성한다. ①은 필수 제품 범위이며 M0부터 구조를 검토한다. 지도 구현이 뒤라는 이유로 전체 프로젝트 설명을 범위에서 제외하지 않는다.

**목표:** 서버·DB·하나의 진입점이라는 가정 없이 설명할 수 있는 데이터와 화면을 먼저 만든다.

위 9종에 더해 작은 지도·규칙 데이터로 해당 공통 필드도 검증한다. 합성 자료는 합성이라고 표시하고 실제 저장소 추적 성공으로 세지 않는다. 실제 자료는 출처·커밋·추적 위치를 기록한다. **복합 부분 결과와 프레임워크/에이전트 사례를 단순 웹 사례보다 먼저 렌더링한다.**

**게이트:** 모든 픽스처가 사실 상태와 의도한 설명을 잃지 않고 렌더링되며, 비웹 사례 때문에 공통 모델을 우회하는 필드·전용 화면이 필요하지 않을 것.

- 전체 “범용 지원 완료”로 광고하지 않고 검증한 유형·언어·사례와 남은 범위를 README에 적는다.

### 7.3 M1.5 — 여러 프로젝트 유형의 골든셋과 회귀 평가

**목표:** 특정 웹 프로젝트에서만 좋아지는 변경을 찾아낼 수 있게 한다.

구현 상태(2026-09-06): [18개 후보](../eval/cases.md), [루브릭](../eval/rubric.md), 소스 역할 비교·회귀 탐지·해시에 묶인 검토 양식을 구현했다. [실행 가이드](../docs/evaluation.md)에 재현 방법을 기록했다. S1.5.3의 사람 정답 확정과 S1.5.5의 승인 베이스라인은 대기 중이다. 저장된 후보 재실행은 독립 모델 생성 평가와 구분하며, 최종 게이트 통과 전에는 M1.5 완료나 IR 동결을 선언하지 않는다.

| 단계 | 산출물 | 완료 기준 |
| :--- | :--- | :--- |
| S1.5.1 저장소 확정 | `eval/cases.md` | 공개 저장소 최소 6곳·3개 언어. 6유형을 모두 포함하고 각 커밋 고정 |
| S1.5.2 18케이스 | 유형별 3케이스 | 일반 사례, 조건·경계 사례, 최소 또는 동적·부분 결과 사례를 유형별로 구성 |
| S1.5.3 사람이 확인한 정답 | 노드·핵심 관계·규칙·근거·한계 | 잘못 그리면 안 되는 관계와 설명에서 빠지면 안 되는 사실을 명시 |
| S1.5.4 평가 루브릭 | `eval/rubric.md` | 아래 정확성·이해 가능성·범용성 축과 측정 방법을 고정 |
| S1.5.5 베이스라인 | `eval/runs/<date>-baseline.md` | 18케이스 전량 실행. 유형별 점수·비용·탐색량·실패 유형, 스킬/모델·커밋·생성 조건 기록 |

**평가 축**

1. **대상·범위 정확성:** 다른 기능을 골랐는지, 포함·제외 범위를 어겼는지.
2. **구성과 관계 정확성:** 누락·과잉, 방향·순서 오류. 존재하지 않는 관계를 확정한 경우를 가장 무겁게 평가한다.
3. **근거 유효성:** 위치 검사와 내용 검토 결과를 따로 측정한다.
4. **설명·규칙 사실성:** 캡션, 조건, 숫자, 단위, 반환·종료·실패 설명이 맞는지.
5. **이해 가능성:** 처음 보는 사람이 목적·입력·결과·동작·한계를 설명하는지. 관련 없는 질문은 강제로 채우지 않는다.
6. **범용성:** 불필요한 웹 개념 삽입, 유형별 전용 렌더러, 작은 설명·정적 관계의 오판 여부.

**통과 기준**

- 존재하지 않는 관계의 **확정 표기 0건**, 수치·조건의 사실 오류 0건, 무근거 검증 완료 표시 0건.
- 케이스별 정답에 있는 핵심 노드·관계의 누락률을 기록한다. `complete`로 표시한 결과에는 정답의 필수 사실 누락이 없어야 한다.
- 미해소가 정답인 사례는 적절한 `partial/insufficient`와 한계를 표현해야 한다. 모든 케이스를 성공 상태로 만드는 것을 목표로 삼지 않는다.
- 유형별 이해 가능성 검토에서 핵심 동작을 거꾸로 이해하게 하는 설명이 없어야 한다.
- 평균 점수가 특정 유형의 실패를 가리지 않도록 유형별 결과를 함께 공개한다.

**운영**

- 이후 공통 지침·스킬 변경은 유형별 1개씩 최소 6케이스와 과거 실패 사례를 재평가한다.
- 특정 프로파일 변경도 해당 유형 3케이스와 다른 유형 3케이스 이상으로 영향 범위를 확인한다.
- 스키마·공통 렌더러·검증기 변경은 전체 골든셋을 재검증한다. 표시만 바꾸는 변경은 데이터/의미 검사와 해당 렌더링 QA를 수행하고, 분석 결과가 바뀌는 경우 전체 생성 평가도 다시 한다.
- 확정 관계 오검출·규칙 사실 오류가 생기거나 기존 통과 사례가 퇴행하면 수정 또는 되돌린 뒤 통과한다.
- 베이스라인 이후 IR을 바꾸면 버전을 올린다. 모델이 달라진 평가 결과도 구분해 기록한다.

### 7.4 M2 — 복합 동작·확장·반복의 정확성

**목표:** 모든 초기 유형에서 현실적인 분기·역방향 제어·실패를 설명한다. 비HTTP 지원의 시작을 이 단계로 미루지 않는다.

구현 상태(2026-09-06): 복합 탐색 지침, 조건·분기·병렬/순서 미정 표시, 필수 행동 주장·경로 평가와 [복합 사례 6개](../eval/m2/discovery.md)를 추가했다. 기존 18개를 보존한 24개 구성이며, 같은 모델로 여러 패키지·프로파일의 경계를 표현한다. 검증 결과와 실제 확인 범위는 [M2 기록](../eval/reports/m2-verification.md)에 정리한다. 사람 사실·이해도 검토 및 승인 베이스라인은 계속 대기 항목이며, 타 언어 프로세스 간 임의 연결의 완전 분석을 검증했다는 뜻은 아니다.

| 단계 | 내용 | 완료 기준 |
| :--- | :--- | :--- |
| S2.1 실패·대안 경로 | 예외, 잘못된 입력, 대체 결과 | 실제 분기 지점과 조건을 표현하고 정상 경로와 구분 |
| S2.2 반복·종료 | 재시도, 반복 변환, 에이전트 실행 루프 | 총 시도/재시도·설정 덮어쓰기·종료 조건을 근거로 설명 |
| S2.3 확장·역방향 제어 | 플러그인 선택, 콜백, 다중 구현체 | 등록과 호출을 구분. 동적 대상은 불확실성 유지 |
| S2.4 비동기·병렬 | 이벤트·작업 그래프·병렬 도구/단계 | 순서가 없는 동작에 순서를 만들지 않고 합류·실패 범위 명시 |
| S2.5 상태·자원 | 메모리·세션·파일·연결·체크포인트 | 읽기/쓰기, 생성/해제, 재진입·멱등성 등 확인한 계약 설명 |
| S2.6 혼합 프로젝트 | 여러 패키지·언어·프로파일 연결 | 저장소 경계와 미해소 연결을 보존. 모델 전체 재설계 없이 표현 |
| S2.7 회귀 평가 | 유형별 복합 사례 1개 추가 | 동작 골든셋 24케이스. 기존 18케이스 퇴행 없음 |

### 7.5 M3 — 규칙과 이유 설명

**목표:** 같은 대상의 “왜 이렇게 동작하는가”를 코드 없이 설명한다.

구현 상태(2026-09-07): S3.1–S3.6의 규칙 탐색 지침, 공통 사실을 재사용하는 규칙 초안·짝 페이지 생성, 조건 비교·입력/결과·상태 그림과 ②↔③ 이동을 구현했다. 기존 동작 24개에 같은 대상의 규칙 6개를 추가해 자동 검증한다. `rules[]`의 이유·예외도 같은 근거 판정을 따르며, 검증에서 제외된 주장에 의존하는 그림은 생략한다. [소스 읽기 기록](../eval/m3/discovery.md)과 [M3 검증 기록](../eval/reports/m3-verification.md)에 실제 범위와 결과를 남긴다. 독립적인 사람의 사실·이해도 게이트는 대기 중이며 다음 구현 범위는 M4다.

호출 예:

~~~text
$code-flow 파일 변환 옵션의 적용 순서를 설명해 줘 --explain
$code-flow 플러그인 초기화 생명주기를 설명해 줘 --explain
$code-flow 에이전트의 도구 반복과 종료 조건을 설명해 줘 --explain
~~~

| 단계 | 산출물 | 완료 기준 |
| :--- | :--- | :--- |
| S3.1 규칙 탐색 | `rule-checklist.md` | 입력 제약, 기본값/우선순위, API·자원 계약, 생명주기, 권한, 실패·재시도·종료 규칙 포함 |
| S3.2 공통 IR 활용 | 검증된 `rules[]` | ②의 검증된 대상·근거에 규칙을 추가. 독립적인 사실 그래프를 새로 만들어 ②와 어긋나지 않음 |
| S3.3 규칙 검증 | 위치·내용 검토 | 수치·조건·예외의 적용 범위 확인. 미검증 수치 규칙은 본문 제외 |
| S3.4 자유 형식 페이지 | `visual-primer` 결과 | 상황 비교·입력/결과·상태 그림 등 적절한 표현. 코드·원문 프롬프트·식별자만의 설명 없음 |
| S3.5 짝 페이지 연결 | ②↔③ | 대상·범위·언어·스냅샷 일치, 차이가 나면 표시·재생성 안내 |
| S3.6 평가 | 6유형의 규칙 설명 각 1개 이상 | 기존 동작 24케이스를 유지하고, 같은 대상의 규칙 산출물 최소 6개 추가 평가 |

②의 출력용 IR에서 제거한 검증 자료가 필요하면 실제 소스에서 다시 확보한다. 낡은 HTML에 “검증됨”이라고 적혀 있다는 이유로 새 규칙을 확정하지 않는다.

소스 기반 규칙 페이지는 주제에 맞게 그림의 종류·수·순서를 조합한다. 공통 화면 틀과 색상·다크모드·근거·링크는 재사용하며, 일반 개념을 설명하는 `visual-primer`의 자유 작성 방식도 유지한다. 수동 그룹 편집이나 예외 다이어그램의 새 색상 체계는 이번 M3 구현에 포함하지 않는다.

**게이트:** 규칙 사실 오류 0건, 처음 보는 독자의 핵심 규칙 오해 0건. 웹의 업무 규칙 외에 라이브러리·프레임워크·에이전트 규칙이 실제로 포함될 것.

### 7.6 M4 — 재생·탐색 사용성 개선

구현 상태(2026-09-07): S4.1–S4.5의 키보드 탐색, 1×/1.5×/2×와 직접 단계 선택, 모션 없는 설명, 모바일 패널 크기 조절, 노드·시나리오·스텝 링크 복원을 구현했다. 배속·정지·재개는 현재 단계의 진행 지점을 유지하며 링크로 열 때 자동재생하지 않는다. 없는 대상·다른 설명의 링크는 기본 화면과 안내로 처리한다. 기존 동작 24개와 규칙 6개를 유지해 검증하며 [M4 검증 기록](../eval/reports/m4-verification.md)에 결과를 남긴다. 독립적인 사람의 사실·이해도 게이트는 계속 대기 중이며 다음 구현 범위는 M5의 프로젝트 전체 지도다.

| 단계 | 내용 | 완료 기준 |
| :--- | :--- | :--- |
| S4.1 키보드 조작 | 노드 선택, 스텝 이동, 재생 토글 | 입력 요소와 단축키 충돌 없이 조작 가능 |
| S4.2 재생 제어 | 배속, 긴 시나리오 이동 | 1x/1.5x/2x 및 단계 이동. 순서 없는 설명에는 불필요한 제어 없음 |
| S4.3 모션·텍스트 대안 | 정적 상태의 정보 동등성 | 모션을 꺼도 같은 관계·상태·경고를 이해 가능 |
| S4.4 모바일 | 패널/하단 드로어, 확대·탐색 | 좁은 화면에서 조작 가능하고 본문 가로 스크롤 없음 |
| S4.5 딥링크 | 노드·시나리오·스텝의 URL 해시 | 새로 열어도 해당 상태 복원. 없어진 ID는 안전한 기본 화면과 안내 |

**게이트:** 최소 유틸리티·프레임워크·에이전트·복합 그래프에서 같은 조작 체계가 통할 것.

### 7.7 M5 — 범용 `codebase-atlas` 프로젝트 지도

구현 상태(2026-09-07): S5.1–S5.4의 실제 저장소 탐색 지침, 책임 구역·관계·범위가 명시된 기능 목록, 선택한 상세 설명만 조립하는 도구와 ①↔②↔③ 이동을 구현했다. 구역·기능은 각자의 근거 판정을 유지하고, 상세 페이지에서 돌아오면 지도 선택·구역·확대·이동 위치를 복원한다. 여섯 공개 저장소의 새 지도와 기존 동작 24개·규칙 6개를 함께 자동 검증한다. [소스 읽기 기록](../eval/m5/discovery.md), [사용 안내](../docs/project-maps.md), [M5 검증 기록](../eval/reports/m5-verification.md)에 범위와 결과를 남긴다. S5.5의 독립적인 사람 이해도 검토와 앞 단계의 승인 베이스라인은 대기 중이다. 계획된 M0–M5 구현 범위는 갖췄으며 최종 게이트 통과나 IR 동결을 선언하지 않는다.

**목표:** 저장소 전체의 목적과 구성을 이해하고 관심 있는 기능의 ②③으로 내려갈 수 있게 한다.

| 단계 | 산출물 | 완료 기준 |
| :--- | :--- | :--- |
| S5.1 목적·구역 | 저장소/패키지 지도 | 빌드·디렉터리·공개 표면·책임에 근거. 작은 프로젝트를 억지로 5~9개 구역으로 나누지 않음 |
| S5.2 관계 | 의존·등록·호출·데이터 관계 | 같은 신뢰·검증 규칙 적용. 디렉터리 인접성을 실제 의존으로 표현하지 않음 |
| S5.3 설명 대상 목록 | 기능·사용 사례·생명주기 목록 | 웹 라우트뿐 아니라 명령·공개 API·훅·에이전트 실행·데이터 작업 포함 |
| S5.4 드릴다운 | ①↔②↔③ 이동 | 생성된 설명은 링크, 미생성 설명은 명령 복사. 전체 하위 페이지 선생성 없음 |
| S5.5 실전 QA | 유형별 지도와 이해 검토 | 골든셋의 6유형에서 지도 생성. 처음 보는 사람이 목적·주요 부분·대표 기능을 설명 가능 |

구역은 크기에 따라 묶거나 펼쳐 설명하되 서버의 기술 계층을 기본 분할 기준으로 삼지 않는다. 라이브러리는 공개 기능군, 프레임워크는 코어와 확장 지점, 에이전트는 실행 제어·도구·상태 등 **실제로 확인한 책임**을 따른다.

**게이트:** 지도에서 선택한 대상과 하위 설명의 범위가 일치하고, 여러 프로젝트 유형에서 세 단계의 탐색이 완성될 것. ①은 선택적인 별도 제품으로 돌리지 않는다.

### 8.3 유지해야 할 경계

- 범용성은 동일한 설명 계약을 여러 프로젝트에 적용한다는 뜻이다. 임의의 저장소를 완전 자동 분석한다고 선언하지 않는다.
- 프로젝트별 지침이 부족하면 공통 탐색으로 확인한 범위와 미해소 사항을 출력한다. 익숙한 웹 구조를 대신 채워 넣지 않는다.
- 동적 모델 응답·런타임 로딩·외부 서비스 내부는 정적 코드만으로 알 수 없는 지점으로 남긴다.
- 결과 HTML의 Git 커밋 여부는 사용자가 정한다. 제품이 일률적인 커밋 정책을 강제하지 않는다.
- 사내 케이스를 추가하면 기본 공개 골든셋과 별도로 저장소 밖 또는 명시적으로 제외한 경로에서 관리한다. 공개 정답 파일에 내부 경로·심볼·테이블 정보를 섞지 않는다.
- 이 계획 개정의 산출물은 개발 계획이다. 구현·실전 분석·사람 검토의 완료 여부는 실제 작업과 기록으로 별도 확인한다.

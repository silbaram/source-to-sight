# 처음 보는 사람을 위한 생성 문서 개선 계획

- 작성일: 2026-09-25
- 상태: 개선 방향 정리
- 구현·자동검사 상태: 미착수
- 독자 검증 상태: 미착수
- 대상: 프로젝트 지도, 기능 설명, 규칙 그림과 이를 만드는 공통 생성 지침
- 목표 독자: 프로젝트를 처음 접하는 개발자와 소프트웨어 개발 지식이 없는 사람

## 1. 목표

문서를 처음 연 사람이 코드를 읽거나 작성자에게 질문하지 않고도 다음 내용을 이해할 수 있게 한다.

1. 어떤 사람이 어떤 상황에서 사용하는 프로젝트인가?
2. 무엇을 넣거나 요청하면 어떤 결과를 얻는가?
3. 대표 기능은 어떤 일을 하고, 중요한 조건에 따라 결과가 어떻게 달라지는가?
4. 저장·조회·다른 서비스 요청 등 서로 다른 동작은 무엇인가?
5. 더 알고 싶을 때 기능 설명, 판단 기준, 구현 위치를 어디서 확인하는가?

모든 독자에게 쉬운 설명을 먼저 제공하고, 개발자가 필요로 하는 내부 구성과 근거를 단계적으로 펼친다. 별도의 독자 모드 선택을 먼저 요구하지 않는다. 쉬운 설명에서도 중요한 조건·실패·불확실성을 보존한다.

## 2. 현재 검토 결과

실제 생성 문서 11개의 설명 데이터와 생성 지침을 검토했다. 프로젝트 지도·기능 상세·규칙 그림의 대표 화면을 브라우저에서 확인했다. 실제 초심자 참여를 통한 이해도 검증은 아직 수행하지 않았다.

| 문제 | 확인한 상태 | 개선 방향 |
| --- | --- | --- |
| 독자 목표가 유지보수에 치우침 | 생성 지침이 변경 위치·영향·구현·테스트 탐색을 우선함 | 프로젝트 목적과 사용 결과 이해를 공통 목표로 설정 |
| 내부 구성이 기능보다 먼저 등장 | 기본 화면이 패키지·실행 환경·내부 연결부터 보여줌 | 목적·대표 사용 상황·입력과 결과를 앞에 배치 |
| 프로젝트 전체 입력·결과가 숨겨짐 | 현재 구성 화면에서는 해당 영역을 CSS로 숨김 | 핵심 입력·결과를 기본 노출 |
| 모바일에서 핵심 내용에 늦게 도달 | 390 × 1000 화면에서 첫 기능 카드가 문서 상단 약 2,307px 아래에 위치 | 기능 탐색과 대표 설명을 내부 구성보다 먼저 배치 |
| 작성된 예시가 표시되지 않음 | 영역의 입력·결과 예시는 구형 영역 화면에서만 사용됨 | 현재 구성·기능 화면에서도 범위가 맞는 예시에 접근 가능하게 함 |
| 전문 용어에 대한 풀이가 부족 | 스키마·앵커·파일 지문·커밋·등록·의존 등이 설명 없이 등장 | 쉬운 표현을 먼저 쓰고 필요한 용어를 가까이 설명 |
| 첫 독자 이해도 검증이 완료되지 않음 | 자동 검사는 표시·탐색·근거·대비 등을 확인하며, 이번 검토에서 실제 독자 참여 검증은 수행하지 않음 | 문서 내용 검토와 실제 첫 독자 검증을 별도 완료 기준으로 추가 |

모바일 위치 측정은 현재 유지보수 예제의 관찰값이며, 모든 프로젝트의 결과를 대표하는 수치가 아니다.

## 3. 유지할 원칙

- 코드 본문·발췌·원시 구현 식은 화면, 숨김 내용, 검색 결과, 설명에 포함된 데이터에도 넣지 않는다.
- 파일·줄 위치, 검토 상태, 검색용 구현 식별자는 기존 목적에 맞게 유지한다.
- 동작은 실제 소스와 검토된 근거에서 설명한다. 쉽게 보이게 하려고 DB·외부 API·실행 순서·사용자 효과를 만들어 넣지 않는다.
- 라이브러리·도구·에이전트·웹서비스를 모두 하나의 서비스 구조에 맞추지 않는다. 사용자가 다른 프로그램인 프로젝트도 그대로 설명한다.
- 카드 위치와 기능 나열 순서는 실행 순서를 의미하지 않는다. 순서가 확인된 경로만 단계별 처리로 표현한다.
- 조건·실패·병렬 실행·외부 경계·미확인 상태를 단순화 과정에서 삭제하지 않는다.
- 기본 처리 카드는 화살표 없이 읽을 수 있게 하고, 기록된 연결은 필요할 때 펼친다.
- 기존 오프라인 동작, 한·영 지원, 테마, 키보드 탐색, 문서 간 왕복 링크를 유지한다.

## 4. 문서별 설명 순서

### 4.1 프로젝트 첫 화면

| 순서 | 독자가 얻는 답 | 표시 내용 |
| --- | --- | --- |
| 1 | 무엇이며 왜 쓰는가? | 프로젝트 이름, 목적, 확인된 사용 대상과 상황 |
| 2 | 무엇을 주고 무엇을 얻는가? | 대표 입력과 결과를 쉬운 말로 나란히 표시 |
| 3 | 실제로 어떤 식으로 쓰는가? | 검토된 대표 사용 예시 하나와 주요 기능 바로가기 |
| 4 | 어떤 기능이 있는가? | 기능별 목적·요청·결과와 간결한 역할 설명 |
| 5 | 무엇으로 구성되어 있는가? | 패키지·실행 환경·저장소·외부 연결 등 기술 구성 |
| 6 | 어디까지 확인했는가? | 상세 범위, 근거, 구현 위치와 검사 정보 |

기본 첫 화면에서 목적과 확인된 대표 입력·결과를 확인할 수 있게 한다. 자료가 없는 항목은 6.3의 기준에 따라 미기록 상태를 안내한다. 대표 사용 예시가 없으면 예시 영역은 생략하고 확인된 주요 기능으로 이어진다. 내부 구성 전체를 스크롤해야 주요 기능에 도달하는 배치를 없앤다. 기술 구성은 기능 설명 아래에 두고 필요에 따라 펼친다.

중요한 미확인 상태와 설명의 해석을 바꾸는 한계는 해당 설명 가까이에 남긴다. 전체 근거 목록과 세부 메타데이터만 뒤로 보낸다.

Source to Sight의 설명 방향 예시:

> 프로젝트 코드와 알고 싶은 질문을 전달하면, 코딩 AI가 설명을 작성하고 이 도구가 브라우저에서 읽는 설명서로 묶습니다.

이 문장은 설명 방식의 예시다. 다른 프로젝트에 복사하지 않으며, 구체적인 사용 상황과 결과는 각 프로젝트의 근거에서 작성한다.

### 4.2 기능 설명

- 상단에서 기능의 목적, 확인된 입력·결과를 바로 보여준다. 입력이나 결과가 기록되지 않았으면 해당 항목의 미기록 상태를 안내한다.
- 대표 처리 내용을 먼저 읽고, 조건·실패·대안 경로를 이어서 확인할 수 있게 한다.
- 확인된 처리 순서가 있으면 해당 경로로 바로 들어갈 수 있게 한다. 순서가 없는 기능은 역할과 관계로 설명한다.
- 처리 카드에는 구체적인 행동, 대상, 짧은 설명을 표시한다. 예: 주문 정보 저장, 결제 서비스에 승인 요청.
- 경로·묶음·보기 전환 등 조작 도구가 본문보다 많은 공간을 차지하지 않도록 정리한다. 같은 기능을 중복 선택하게 하는 제어는 줄인다.
- 상세 패널은 하는 일·받는 정보·만들어지는 결과·중요 조건을 먼저 보여주고, 구현 위치와 테스트 연결은 펼쳐 확인하게 한다.

### 4.3 규칙 그림

- 어떤 상황에서 필요한 판단인지 먼저 설명한다.
- 조건을 바꾸면 결과가 어떻게 달라지는지 그림과 짧은 문장으로 보여준다.
- 중요한 예외와 실패 결과를 함께 표시한다. 근거가 있는 경우에만 이유를 설명한다.
- 앞 문서를 읽지 않고 들어온 독자도 이해하도록, 필요한 대상과 용어를 다시 짧게 소개한다.
- 현재의 조건 비교·결과 그림·근거 접기 구조를 유지하고 세 문서에 같은 독자 기준을 적용한다.

## 5. 용어와 화살표 기준

### 5.1 문장 작성

- 문장에는 누가, 무엇을, 어떻게 처리하는지가 드러나게 쓴다.
- 모듈명·함수명보다 실제 역할과 업무 대상을 먼저 쓴다.
- 필요한 전문 용어는 첫 등장 위치에 짧은 뜻을 함께 제공한다. 필수 설명을 마우스 올리기에만 숨기지 않는다.
- 쉬운 말과 기술 용어를 연결하되, 문맥에 따른 뜻의 차이는 유지한다.
- 여러 용어를 단순 문자열 치환으로 바꾸지 않는다. 설명 대상과 실제 동작을 확인한 뒤 문장을 다시 작성한다.

| 현재 표현 | 설명 방향 예시 | 주의점 |
| --- | --- | --- |
| 스키마 검사 | 설명에 필요한 항목이 빠짐없이 올바른 형식으로 작성됐는지 확인 | 실제로 검사하지 않는 내용 정확성까지 보장한다고 쓰지 않음 |
| 앵커·파일 지문 | 근거로 삼은 코드 위치와 작성 당시 파일을 식별할 정보를 기록 | 코드 내용 자체를 보여주지 않음 |
| 커밋 비교 | 설명을 작성할 때와 현재의 코드 버전이 같은지 확인 | 파일 내용 재검사와 버전 비교를 같은 검사로 취급하지 않음 |
| DB 저장 | 데이터베이스(DB)에 주문 정보를 저장 | 저장 대상과 성공 보장은 근거 범위 안에서 설명 |
| API 요청 | 다른 서비스에 결제 승인을 요청 | API라는 이유만으로 외부 서비스라고 단정하지 않음 |
| 노드 | 처리 단계 또는 구성 요소 | 화면에서 해당 상자가 나타내는 실제 의미에 맞춤 |

### 5.2 관계 설명

색과 선 모양은 기존 관계 구분을 유지한다. 텍스트만 읽어도 관계의 뜻을 알 수 있도록 설명을 보완한다.

| 관계 | 독자에게 설명할 의미 | 기존 표시 |
| --- | --- | --- |
| 호출·제어 | A가 B에 처리를 요청하거나 다음 처리를 맡김 | 파랑 실선 |
| 데이터 관련 관계 | 읽기·저장·전달·발행·수신 중 기록된 행동과 대상을 설명 | 청록 실선 |
| 의존 | A를 구현하거나 사용하기 위해 B가 필요함 | 회색 파선·열린 화살촉 |
| 등록 | B를 나중에 선택해 사용할 수 있도록 A가 목록 등에 연결해 둠 | 회색 파선·열린 화살촉 |
| 추정·미확인 | 이 연결은 근거가 부족하거나 현재 위치를 확인하지 못한 상태 | 노란 점선과 상태 문구 |

‘등록·의존’이라는 묶음 이름만으로 설명을 끝내지 않는다. 각 연결에는 실제 관계에 맞는 풀이를 붙이고, 두 관계의 뜻을 따로 안내한다. 등록·의존은 실행 순서나 이미 수행된 작업을 보장하지 않는다.

데이터 관련 관계는 아래처럼 행동을 구분한다. 같은 청록색이라고 해서 모두 ‘A가 만든 정보를 B에 전달한다’고 설명하지 않는다.

| 행동 | 설명 예시 | 방향을 해석할 때 확인할 내용 |
| --- | --- | --- |
| 읽기·조회 | 주문 처리 기능이 저장소에서 주문 정보를 읽음 | 조회 요청의 관계 방향과 결과 데이터가 돌아오는 방향을 구분 |
| 저장 | 주문 처리 기능이 주문 정보를 저장소에 기록함 | 기록하는 처리와 저장 대상을 구분하고 저장 성공은 근거 범위에서 설명 |
| 전달 | 한 처리가 받은 정보를 다음 처리에 전달함 | 실제 보내는 쪽·받는 쪽을 확인하며, 보내는 쪽이 데이터를 만들었다고 단정하지 않음 |
| 발행 | 주문 처리 기능이 주문 완료 메시지를 발행함 | 발행 주체와 발행 대상을 확인하며, 소비자의 수신·처리 완료를 보장하지 않음 |
| 수신 | 알림 처리 기능이 메시지 보관소에서 메시지를 받아 처리함 | 메시지를 받는 처리와 출처를 확인하고, 등록된 관계 방향을 임의로 뒤집지 않음 |

화살표는 검토된 관계 유형과 출발·도착 정보를 유지한다. 예를 들어 ‘주문 처리 → 저장소’가 조회 요청을 나타내면 그렇게 설명하고, 조회 결과의 반환 연결은 별도 근거가 있을 때만 표시한다. 설명을 단순화하려고 연결을 뒤집거나 반환 화살표를 만들어 넣지 않는다. 재생 표시도 기록된 관계 방향을 설명하는 것으로 한정하고 실제 데이터 전송의 관찰 결과로 표현하지 않는다.

DB 저장·파일 저장·서비스 요청의 차이는 관계색 외에 처리 카드의 종류·대상·설명으로 전달한다. 선택·재생·키보드 초점에서는 관계색을 유지하고 굵기와 테두리로 강조한다.

## 6. 생성 지침과 데이터 적용

### 6.1 세 스킬의 독자 기준 통일

`codebase-atlas`, `code-flow`, `visual-primer` 모두 다음 순서로 설명을 작성하도록 맞춘다.

1. 근거에서 프로젝트 또는 기능의 목적과 사용 상황을 확인한다.
2. 입력과 결과, 대표 사례를 쉬운 말로 작성한다.
3. 이해에 필요한 처리와 조건만 먼저 설명한다.
4. 필수 용어를 처음 등장하는 곳에서 풀어 쓴다.
5. 내부 구성과 구현 근거를 필요한 깊이로 연결한다.
6. 내용 정확성, 초면 독자의 이해 가능성, 화면 동작을 각각 검토한다.

### 6.2 기존 데이터 우선 활용

- `summary.purpose`, `summary.inputs`, `summary.outputs`, 기능별 설명, `operation`을 우선 활용한다.
- 기존 `region.interface.example`이 현재 화면에서도 사라지지 않게 한다. 예시의 소속 영역·대상·범위를 보존해 해당 설명 가까이에 배치한다.
- 특정 영역의 예시를 프로젝트 전체의 대표 예시로 자동 승격하지 않는다. 여러 영역을 임의로 연결해 사용 시나리오를 만들지 않는다.
- 이해를 돕기 위해 만든 예시는 ‘설명용 예시’로 표시한다. 관찰한 실제 실행 결과와 구분하고 기존 근거 상태에 따른 보류 규칙을 유지한다.
- 기존 필드로 표현할 수 없는 프로젝트 사용 상황이나 용어 풀이가 필요할 때만 선택적 필드 추가를 검토한다. 필드 이름과 소속은 의미·범위·근거 처리부터 정한 뒤 확정한다.
- 새 필드를 추가한다면 내부·공개 스키마, 변환·검증, 원본 보관·재사용, 코드 비노출 검사에 함께 반영한다.
- 기존 JSON은 재작성 없이 계속 렌더링되어야 한다. 정보가 없으면 설명을 지어내지 않고 아래 표시 기준을 적용한다.

### 6.3 자료 유무에 따른 표시와 완료 기준

| 자료 상태 | 표시 기준 | 완료 판단 |
| --- | --- | --- |
| 목적·사용 대상·입력·결과가 확인됨 | 확인한 내용을 쉬운 말로 설명하고 대표 입력·결과는 첫 화면에 표시 | 기록된 의미와 범위를 유지하며 읽을 수 있으면 충족 |
| 핵심 항목이 미기록임 | 해당 위치에 ‘입력 정보 미기록’ 등 부족한 항목을 알리고 확인된 설명은 유지 | 빈칸을 추측으로 채우지 않고 자료 부족을 구분할 수 있으면 표시 기준 충족 |
| 근거가 부족하거나 현재 확인되지 않음 | 상태와 한계를 해당 설명 가까이에 표시하고 기존 보류 규칙을 적용 | 확인된 사실로 오인하게 하지 않고 보류 대상의 본문·예시가 노출되지 않으면 충족 |
| 범위에 맞는 대표 예시가 확인됨 | ‘설명용 예시’로 표시하고 해당 기능·영역에 연결 | 소속 범위와 검토 상태를 유지하면 충족 |
| 대표 예시가 없거나 해당 범위와 맞지 않음 | 예시 영역을 생략하고 확인된 기능 설명으로 연결 | 다른 범위의 예시를 끌어오거나 새 사례를 추측하지 않으면 충족 |
| 해당하지 않는 항목임이 확인됨 | 필요한 경우 ‘해당 없음’과 짧은 이유를 표시 | 단순 미기록을 ‘해당 없음’으로 처리하지 않으면 충족 |

배열이 비어 있거나 필드가 없다는 사실만으로 실제 입력·결과·기능이 없다고 단정하지 않는다. 자료 부족 안내가 올바르면 구현의 표시 기준은 충족할 수 있지만, 프로젝트 설명의 내용이 충분해졌다는 뜻은 아니다. 남은 자료 부족과 추가 검토 범위는 별도로 기록한다.

### 7.1 진행 상태 기록

구현과 독자 검증은 별도 상태로 기록한다. 구현·자동검사에는 수동 화면 확인도 포함한다.

| 구분 | 상태 | 기록 기준 |
| --- | --- | --- |
| 구현·자동검사 | 미착수 / 진행 중 / 완료 | P0·P1 작업과 해당 자동·시각 검사, 9.1 체크리스트를 완료한 경우에만 완료 |
| 독자 검증 | 미착수 / 대기 / 진행 중 / 보완 필요 / 완료 | 검토할 문서와 질문이 준비됐지만 참여 검증을 시작하지 못했으면 대기. 참여 중이면 진행 중, 오해를 수정하거나 재확인해야 하면 보완 필요 |

‘구현·자동검사 완료 / 독자 검증 대기’처럼 두 상태를 함께 보고한다. 실제 참여자가 없는 상태에서 독자 검증을 완료로 바꾸지 않는다. 독자 검증 대기 중에도 독립적으로 수행 가능한 구현·검사는 계속 진행하며, 기다리는 이유와 필요한 다음 작업을 기록한다. 독자 검증에서 코드·문서 수정이 발생하면 영향받는 검사를 다시 수행하고 구현 상태에도 반영한다.

## 8. 검증 계획

### 8.1 자동 검사와 화면 확인

- 첫 화면의 확인된 목적·입력·결과 또는 미기록 안내와 주요 기능의 배치 순서를 확인한다. 기존의 ‘구성이 먼저’라는 테스트 기대도 새 기준으로 바꾼다.
- 입력·결과가 비어 있는 경우와 일부만 기록된 경우, 예시 있음·없음·범위 불일치·근거 미확인을 각각 검증한다. 현재 구성 화면과 기존 영역 화면의 호환을 확인한다.
- 기존 코드 비노출, 근거 상태, 데이터 변환, 대상·범위 일치 검사를 유지한다.
- 프로젝트 → 기능 → 규칙 → 돌아오기, 직접 링크, 검색, 새로고침 후 선택 복원을 확인한다.
- 카드 기본 보기, 연결 펼치기, 실제 경로 재생, 순서 없는 관계의 표현을 확인한다.
- 읽기·저장·전달·발행·수신의 설명이 실제 관계 유형과 출발·도착에 맞는지 확인한다. 조회 요청을 결과 데이터 전달로 잘못 설명하거나 근거 없는 반환 연결을 추가하지 않았는지도 확인한다.
- 한·영, 데스크톱 1440 × 900, 모바일 390 × 844, 밝은·어두운 테마에서 읽는 순서·줄바꿈·겹침·대비를 확인한다.
- 작은 화면에 내용을 맞추기 위해 글자나 그림을 과도하게 줄이지 않는다. 확대·키보드·오프라인 동작도 유지한다.
- 실제 유지보수 문서와 합성 업무 예제를 함께 확인한다. 이 저장소에 없는 DB·API 동작을 실제 문서에 추가하지 않는다.

### 8.2 첫 독자 이해도 검토

프로젝트를 모르는 개발자와 비개발자를 각각 포함한 소규모 검토를 수행한다. 작성자의 구두 설명 없이 문서를 읽게 하고 다음 질문을 확인한다.

검토 문서·질문·담당자·참여자·일정을 기록한다. 참여자나 일정이 정해지지 않았으면 독자 검증은 대기로 남기고, 구현·자동검사 완료와 구분한다.

| 확인 시점 | 질문 |
| --- | --- |
| 첫 화면을 읽은 뒤 | 어떤 프로젝트이며 누가 어떤 상황에서 쓰는가? |
| 입력·결과 설명을 읽은 뒤 | 무엇을 전달하면 무엇을 얻는가? |
| 대표 기능을 읽은 뒤 | 이 기능에서 중요한 처리와 결과는 무엇인가? |
| 조건 그림을 본 뒤 | 어떤 조건 때문에 결과가 달라지는가? |
| 연결을 펼친 뒤 | 이 화살표는 어떤 관계이며 실행 순서를 뜻하는가? |
| 더 알아보려 할 때 | 자세한 기능·판단 기준·구현 위치를 어디에서 찾는가? |

정답 예시는 검토된 소스 범위에서 미리 정한다. 독자가 막힌 용어, 오해한 관계, 설명이 필요한 화면을 기록해 수정한다. 답이 잘못됐을 때 사람에게 추가 설명해 해결한 것으로 처리하지 않고 문서 자체를 보완한다.

자료가 부족한 항목에서는 독자가 ‘이 문서에서는 아직 확인되지 않았다’고 구분할 수 있는지 확인한다. 기록되지 않은 정답을 추측하도록 요구하지 않으며, 확인된 내용의 이해와 자료 부족의 인지를 따로 기록한다. 이 결과로 자료 부족 자체가 해소됐다고 판단하지 않는다.

참여자 수, 검토한 페이지, 답변과 수정 내용을 기록한다. 소규모 검토 결과를 모든 일반인의 이해 가능성으로 확대하지 않는다. 참여 검토 전에는 ‘일반인 이해도 검증 완료’라고 보고하지 않는다.

## 9. 최종 완료 체크리스트

### 9.1 구현·자동검사 완료

- [ ] 세 스킬이 처음 보는 개발자와 비개발자를 공통 독자로 명시한다.
- [ ] 첫 화면에서 확인된 목적·대표 입력·결과 또는 해당 항목의 미기록 안내를 볼 수 있다.
- [ ] 내부 구성을 읽기 전에 확인된 주요 기능과 사용 상황을 읽거나 자료 부족을 알 수 있다.
- [ ] 예시는 범위·자료 유무·검토 상태에 따라 표시·생략·보류되고 실제 실행 결과와 구분된다.
- [ ] 필수 전문 용어와 등록·의존의 뜻을 설명 없이 추측할 필요가 없다.
- [ ] 데이터 관계의 읽기·저장·전달·발행·수신과 방향을 구분하고 근거 없는 연결을 만들지 않는다.
- [ ] 동작·조건·실패·불확실성과 근거가 쉬운 설명에서도 유지된다.
- [ ] 기존 데이터, 링크, 검색, 선택 복원과 코드 비노출이 유지된다.
- [ ] 공통 생성 경로에 변경을 적용하고 대표 HTML을 재생성한다.
- [ ] 해당 자동·시각 검사 결과와 남은 자료 부족을 기록한다.

### 9.2 독자 검증 완료

- [ ] 프로젝트를 모르는 개발자와 비개발자가 작성자의 구두 설명 없이 문서를 검토했다.
- [ ] 검토한 문서·참여자·질문·답변과 자료 부족의 인지 여부를 기록했다.
- [ ] 핵심 의미에 대한 오해를 수정하고 필요한 질문을 다시 확인했다.
- [ ] 남은 한계와 검증 범위를 명시하고 소규모 결과를 전체 독자에게 일반화하지 않았다.

구현·자동검사 완료는 9.1을, 독자 검증 완료는 9.2를 충족한 시점에 각각 기록한다. 전체 계획 완료는 두 상태가 모두 완료된 경우에만 판단한다. 현재 두 작업은 미착수이며, 이 문서는 구현 또는 이해도 검증의 완료 보고가 아니다.

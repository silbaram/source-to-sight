# Repository discovery

Keep a short ledger of what you read, what it supports, and what remains outside the map. Read only relevant profile guidance from the installed code-flow companion.

1. Establish the repository/package root, revision and build boundaries. Read manifests and the project introduction. Find public exports, entry commands, registrations, examples and tests before choosing groups.
2. Identify responsibilities from implementations and contracts. A library may expose distinct cache policies, a framework may separate registration from callback dispatch, and an agent may separate orchestration, model adapters, tools and memory. These are examples, not mandatory regions.
3. Read both ends of a representative relationship and the call/registration/data site between them. Declaration-only evidence does not prove collaboration. External systems can be boundaries; describe only the local interaction that was read.
4. Select useful capabilities across the discovered surface. Record the exact module, target file/symbol, start/end and exclusions. Existing behavior candidates can supply identity, but reread their source and their correspondence to the map node. A display label or identical function name does not establish scope equivalence.
5. Review each node, relationship, region and capability against its evidence. A region claims shared responsibility, so its evidence must support the group as well as the member declarations. Use disjoint display groups; shared dependencies remain real edges. Leave cross-cutting parts ungrouped when that is clearer.
6. Record a useful, bounded set of actual package/folder landmarks in `structureEntries`. Check each path and its local code/config, explain its role briefly, and associate only reviewed owner nodes. Package/build manifests establish package boundaries; an ordinary directory remains a directory. Nested paths express containment, not execution or dependency. Name omitted areas in scope/limitations rather than implying a complete filesystem inventory.

Use source documents to establish purpose and contracts, and source code/configuration for current physical relationships. A document/implementation discrepancy belongs in the limitations with both locations. A helper does not need to read every file, but the map must name omitted packages, implementation interiors and dynamic choices that matter to understanding its coverage.

Stop expanding when the question is answered with readable responsibilities and representative capabilities. Preserve remaining candidates and next attempts. Do not hide additional source-backed core nodes to meet an arbitrary count or invent groups for a small project.

The authoring pipeline performs location/hash verification separately from semantic review. Marking a claim `supported` records the host's source review, not independent human acceptance. Keep `humanReviewed: false` until an actual review occurs.

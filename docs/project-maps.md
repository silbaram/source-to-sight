# 프로젝트 지도 사용 안내

`codebase-atlas`는 AI로 코드를 유지보수할 때 프로젝트를 빠르게 이해하도록 돕습니다. 입구는 **한눈 요약 + 기능 중심 구조 지도**입니다. 기능을 고르면 담당 구성·코드 위치·관련 흐름·규칙이 한곳에 모이고, 더 알고 싶으면 기존 상세 관계도와 그림 중심 규칙 설명으로 이동합니다. 호스트 에이전트가 소스와 문서를 읽어 내용을 작성하고, 공통 생성 도구가 근거와 페이지 연결을 확인해 오프라인 HTML로 만듭니다.

## 처음 보는 유지보수자를 위한 탐색

첫 화면은 프로젝트 목적과 입력·결과, 기능들의 연결을 큰 그림으로 보여 줍니다. 같은 책임은 영역으로 묶고, 선에는 실제 전달 데이터나 요청·의존 관계를 적습니다. 그룹 안에 있다는 이유만으로 실행 순서를 만들지 않습니다.

**프로젝트 연결 → 기능의 데이터 흐름 → 선택한 노드의 규칙 그림**으로 들어갑니다. 상세가 준비된 기능은 관계도에서 바로 열립니다. 상세가 없는 기능과 여러 기능을 담당하는 구성은 역할과 연결, 선택 가능한 기능을 확인합니다. 기능 목록·검색·코드 경로는 펼쳐서 볼 수 있습니다.

상세 흐름의 노드에는 들어오고 나가는 데이터, 판단 규칙, 구현 위치와 테스트 근거가 연결됩니다. 규칙 그림은 선택한 노드의 내용에 집중하고 전체 규칙으로 확장할 수 있습니다. 돌아오면 선택한 처리 지점이나 프로젝트 기능을 다시 보여 줍니다. 그림은 계산·비교·상태 변화 등 규칙에 맞춰 작성하며 코드를 포함하지 않습니다.

유지보수 정보는 원본에서 확인한 위치와 연결입니다. 전체 변경 영향 분석이나 테스트 통과 결과를 뜻하지 않습니다. 기록되지 않은 흐름·규칙·테스트는 추측하지 않고 빈 범위로 남깁니다. 자세한 작성 기준은 [유지보수자를 위한 정보 설계](../skills/codebase-atlas/references/maintenance-story.md)에 있습니다.

## 설치와 요청

설치와 첫 사용을 순서대로 진행하려면 [단계별 퀵스타터](quickstart.md)를 먼저 읽으세요. 이 문서는 지도 화면을 탐색하고 상세 페이지로 이동하는 방법을 설명합니다.

GitHub 저장소에서 모든 스킬을 함께 설치합니다. 프로젝트 지도에는 `codebase-atlas`와 `code-flow`가 필요하며, 규칙 설명까지 만들 때는 `visual-primer`도 사용합니다.

~~~sh
npx skills add silbaram/source-to-sight --global --skill '*'
~~~

폴더를 복사해 설치할 때는 각 스킬의 스크립트·참조 문서·템플릿·라이선스를 함께 보존합니다. Atlas는 실제 설치된 code-flow의 경로를 사용하며, 별도 위치는 `--code-flow-root`로 지정합니다. 검증기가 포함되어 있어 Python 3.10 이상만 있으면 실행할 수 있습니다. 상세 조립 명령은 [스킬의 조립 안내](../skills/codebase-atlas/references/assembly.md)에 있습니다.

~~~text
$codebase-atlas 이 프로젝트의 목적과 주요 구성, 대표 기능을 설명해 줘.
$codebase-atlas 이 라이브러리의 공개 기능과 내부 책임을 지도로 정리해 줘.
$codebase-atlas 에이전트 실행 제어, 도구, 모델, 기록이 어떻게 연결되는지 설명해 줘.
~~~

구역은 확인한 책임에 따라 정합니다. 작은 유틸리티는 노드 하나로 충분할 수 있고, 프레임워크·라이브러리·에이전트는 서로 다른 구성을 갖습니다. 디렉터리 위치만으로 호출 관계를 만들지 않습니다.

## 화면에서 확인하는 흐름

1. 프로젝트 목적과 입력·결과를 확인하고, 큰 관계도에서 기능의 역할과 연결을 봅니다. **지원 구성 포함**으로 개발·사용을 돕는 부분도 확인합니다. 그룹은 공유하는 책임이며 실행 순서를 뜻하지 않습니다.
2. 상세가 준비된 기능을 누르면 해당 범위의 데이터 흐름이 열립니다. 선의 데이터·요청·조건을 따라가고, 기본·오류 등 기록된 경로를 골라 단계별로 살펴봅니다.
3. 처리 노드를 누르면 입력·출력 연결과 판단 규칙이 모입니다. **이 규칙을 그림으로 이해하기**로 해당 노드의 규칙 그림에 들어갑니다. **전체 규칙 보기**로 나머지 설명도 펼칠 수 있습니다.
4. 구현을 바꾸기 전에는 노드의 **유지보수 · 구현 위치와 근거**, 관련 연결, 테스트 근거를 펼칩니다. 기록된 테스트 위치는 실행·통과 결과가 아닙니다.
5. **기능 목록에서 찾기**와 **통합 검색** 또는 `Ctrl+K` / `Cmd+K`로 기능·구성·경로를 찾습니다. 목록의 기능 요약은 닫기 또는 `Esc`로 닫을 수 있습니다. **패키지·폴더 펼쳐 보기**에서는 물리적 위치를 확인합니다.
6. 그림에서 기능 흐름으로 돌아오면 선택한 노드를, 프로젝트로 돌아오면 선택한 기능을 보여줍니다. 분석 범위와 중요한 미확인 사항은 별도로 확인합니다. 표시된 연결이 전체 변경 영향 목록을 뜻하지는 않습니다.

입구의 미생성 기능에는 **상세 생성 요청 복사**가 나옵니다. 미생성은 기능이 없다는 뜻이 아니라 상세 HTML이 준비되지 않았다는 뜻입니다. 복사한 요청을 호스트에 전달하면 정확한 대상과 범위로 상세 설명을 작성합니다. 브라우저의 버튼 자체가 분석이나 모델 실행을 시작하지는 않습니다. 새 상세 설명을 만든 뒤 지도를 다시 생성하면 링크가 갱신됩니다. 소스 시점·언어·대상·범위가 맞지 않거나 이 지도로 돌아오는 링크가 없는 기존 HTML도 생성 요청으로 표시합니다. 기존 상세를 지도에 연결하려면 그 내부 입력을 페이지 목록에 명시해 지도와 함께 다시 조립합니다.

입구의 기능 수는 **이번 분석에 기록된 대표 기능 수**이며 저장소 전체 기능을 조사했다는 뜻이 아닙니다. 패키지·폴더 정보는 원본 JSON의 선택 필드 `structureEntries`에 보관합니다. 예전 JSON에 이 정보가 없으면 미기록 안내를 표시하고 기존 다이어그램은 유지합니다. 에이전트에 실제 경로와 근거를 검토해 구조 정보를 추가해 달라고 요청하세요. HTML만으로 구조를 추측하거나 모든 파일을 자동 나열하지 않습니다.

선택 화면은 담당 노드에 연결된 `scenarios`와 `rules`를 사용합니다. 같은 구성을 포함하는 흐름은 관련 설명이지 선택 기능만의 정확한 실행 경로를 보장하지 않습니다. 시나리오 전체를 유지하며 조건·병렬·분기 표시를 함께 보여 줍니다. 데이터가 없으면 해당 부분은 숨겨지고, 없는 내용을 추측해 만들지 않습니다. 테스트도 기능이나 담당 구성에 명시적으로 연결된 `kind: test` 근거만 표시합니다. 추가하려면 소스·문서 검토 후 내부 JSON을 갱신해야 합니다. 숫자가 있는 규칙은 근거와 내용이 확인되지 않으면 렌더링 전에 제외됩니다.

시나리오가 있는 지도에서는 상세 다이어그램의 흐름 재생기도 활성화됩니다. 없는 경우 재생기는 나타나지 않습니다. 모든 지도는 공통 캔버스 템플릿의 다크모드, 검색, 이동·확대, 모바일 설명 패널을 사용합니다. UI만 갱신할 때는 보관한 내부 JSON으로 다시 빌드하면 됩니다. 소스가 달라졌다면 영향받는 근거와 설명을 먼저 검토합니다.

최종 탐색 흐름은 **프로젝트 맵 → 기능·상세 흐름 → 핵심 비즈니스 로직의 그림 설명**입니다. 마지막 단계는 [OAuth 예시](../assets/oauth-visual-primer-example.html)의 그림 중심 설명 방식을 코드로 확인된 규칙에 적용합니다. 주제마다 그림과 조작은 달라지며, 예시의 OAuth 내용이나 화면을 그대로 복제하지 않습니다. 기존 버전 1 레이아웃은 간단한 규칙 참고 화면으로 계속 열 수 있지만, 새 그림 설명은 맞춤형 버전 2 레이아웃을 기본으로 작성합니다.

## 사용 결과

`codebase-atlas`와 `code-flow`를 설치한 뒤 호스트 에이전트에 대상 프로젝트 설명을 요청합니다.

| 지도 유형 | 보여 주는 구성 |
| --- | --- |
| AI 에이전트 | 반복 제어, 실행 방식, 모델·도구·기록 |
| 프레임워크 | 플러그인 등록, 훅 호출, 결과 처리 |
| 라이브러리 | 캐시 정책, 기본 저장 구조 |
| 유틸리티 | 단일 문자열 정리 함수와 입력 계약 |
| 이벤트 | 신호 이름 공간, 등록·전달·참조 관리 |
| 웹 | 경로 등록·탐색, 보정, 외부 처리기 |

생성된 HTML은 대상 프로젝트에 대한 기록된 분석 결과입니다. 지도에 빠진 부분과 동적으로 결정되는 내용은 **설명 범위와 한계**에 표시합니다.

## 원본 데이터 보관과 재생성

출력 위치를 지정하지 않으면 `docs/atlas/<project-key>.html`을 사용합니다. 지도 빌더는 HTML 폴더 아래 `_internal/<지도 파일명에서 확장자를 뺀 이름>/`에 분석 원본을 자동 보관합니다. 예를 들어 `build/source-to-sight/project.html`의 원본은 `build/source-to-sight/_internal/project/`에 있습니다. 별도의 내부 위치는 `--internal-dir`로 지정합니다.

지도 원본 `atlas.internal.json`, 기능별 동작·규칙 원본 `*.internal.json`, 원본 그림 구성 `*.layout.json`, 입력과 HTML 경로를 연결하는 `pages.json`을 재사용합니다. 요청하지 않은 상세는 새로 만들지 않으며, 지도만 갱신해도 기존 상세 원본과 연결 목록은 보존합니다. 화면만 다시 만들 때는 이 JSON으로 렌더링하고, 소스가 바뀌면 영향을 받는 근거와 설명을 검토해 JSON을 갱신합니다. 자동 Git 변경 분석이나 HTML 부분 패치 기능은 아닙니다.

`render.json`은 검증 근거가 제거되거나 표시할 내용만 남은 화면용 데이터라서 원본 JSON을 대신하지 않습니다. `_internal/`에는 소스 발췌가 들어갈 수 있으므로 공유와 정적 사이트 게시에서 폴더 전체를 제외합니다. 자세한 명령과 기존 원본의 이전 방법은 [조립 안내](../skills/codebase-atlas/references/assembly.md#re-render-refresh-and-share)에 있습니다.

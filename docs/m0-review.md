# M0 개발 계획 대비 검토

검토일: 2026-09-06. 대상은 현재 작업 디렉터리의 구현과 [v5 개발 계획](../plans/source-to-sight-evolution-plan.md) 중 M0다. M1 이후의 미구현 기능은 M0 결함으로 세지 않았다.

**수정 후 상태: 리뷰에서 지적한 세 문제를 수정하고 회귀 검증을 통과했다.** 검증 테스트 28개와 데스크톱·좁은 화면 브라우저 테스트 48개가 통과했다. 아래 번호별 설명과 행번호는 수정 전의 재현 기록이다.

| 지적 사항 | 수정 결과 | 회귀 검증 |
| --- | --- | --- |
| 이전 페이지와 잘못된 스냅샷 일치 | 검토 해시와 현재 관측 해시를 분리했다. 실패한 근거는 일치로 판정하지 않으며, 미커밋·미확인 상태는 기록된 근거 파일 집합 전체를 비교한다. 경고에 연결 페이지 경로를 표시한다. | 파일 변경·삭제 후 이전 규칙 페이지 연결, 일부 파일만 일치하는 경우, 확인된 동일 커밋, 이전 출력 형식 호환성 |
| 상태 전이 조건 누락 | 전후 상태와 별도로 변경 조건, 검토 사유, 근거를 표시한다. CLI 표준 픽스처에 세부 동작과 조건부 상태 전이를 추가했다. | 실제 브라우저에서 조건 텍스트와 전이 근거가 표시되는지 확인 |
| 구역의 추정·근거 누락 | 구역의 검증 배지와 구역 전용 근거 버튼을 추가했다. 구성 노드의 근거는 별도로 열린다. | 확인·추정·위치 미확인 구역, 구역과 노드의 서로 다른 상태, 키보드 및 모바일 포커스 복귀 |

## 1. 높은 우선순위 — 변경된 소스와 이전 페이지가 같은 스냅샷으로 판정됨

관련 코드: `skills/code-flow/scripts/s2s.py`의 `verify_locations` 161–168행, `source_matches` 180–197행, 연결 확인 294–297행. 계획 §3.3, §4.5 및 S0.6에 해당한다.

재현 절차:

1. `cli-transform` 픽스처와 합성 근거 파일을 임시 디렉터리에 복사한다.
2. 같은 대상의 `logic.html`을 생성한다. 이때 근거 위치 검사는 통과한다.
3. 앵커를 유지한 채 소스 파일 끝에 내용을 추가한다.
4. `workingTreeClean: false`를 기록하고, 앞서 만든 규칙 페이지를 연결하여 동작 페이지 데이터를 다시 조립한다.

관측 결과:

~~~json
{
  "new_location_states": ["failed"],
  "old_location_states": ["passed"],
  "source_matches": true,
  "link_active": true,
  "snapshot_warning": false
}
~~~

내용 불일치 시 `contentHash`가 이전 값으로 남고, 비교 함수는 위치 검증 실패를 고려하지 않는다. 그래서 새 설명은 재검증 실패 상태인데 이전 규칙 페이지와의 시점 차이는 경고하지 않는다. 미커밋 변경이 있는 경우 공통 파일 하나의 해시만 일치해도 `true`를 반환하는 비교 방식 역시 전체 분석 범위의 일치를 입증하지 못한다.

실패하거나 확인하지 못한 근거가 있으면 같은 소스라고 확정하지 않아야 한다. 검토 당시 해시와 현재 관측한 해시를 구분하고, 변경된 작업 디렉터리의 비교 가능 범위를 명시해야 한다. 링크를 유지하더라도 오래되었거나 확인되지 않은 짝임을 표시해야 한다.

## 2. 중간 우선순위 — 상태 전이의 조건이 화면에서 누락됨

관련 코드: `skills/code-flow/templates/viewer.js` 122–127행. 계획 §5.1의 상태 트리거, §4.1 및 S0.5에 해당한다.

검토용 합성 입력에 `대기 → 완료` 상태 전이와 별도의 `trigger`인 “검토용 고유 조건: 저장에 성공했을 때만”을 넣어 렌더링했다. 내부·출력 검증은 통과했고 데이터 스크립트에도 조건이 남아 있었다. 그러나 노드를 클릭한 설명 패널에는 전후 상태와 일반 설명만 표시되었으며 조건은 나타나지 않았다.

상태가 어떤 조건에서 바뀌는지 독자가 알 수 없어 조건부 동작을 무조건적인 변화로 오해할 수 있다. `trigger`를 상태 전이 설명에 표시하고, `plainText`가 조건을 반복하지 않는 예제로 검증해야 한다.

## 3. 중간 우선순위 — 지도 구역의 불확실성과 근거를 볼 수 없음

관련 코드: `skills/code-flow/templates/viewer.js` 370–373행. M0의 최소 지도 계약과 “사실 상태를 잃지 않고 렌더링”한다는 게이트에 해당한다.

`utility-atlas`의 구역을 `confidence: inferred`, `supportStatus: uncertain`으로 설정했다. 출력 IR에는 `displayStatus: uncertain`이 올바르게 계산되지만, 구역 화면은 제목·설명·구성 노드 버튼만 그린다. 구역의 추정 표시, 검토 사유, 근거 확인 수단이 없다. 버튼을 누르면 구역 대신 구성 노드의 “위치·내용 확인” 패널이 열린다.

상단의 전체 부분 분석 표시는 어느 구역 구분이 추정인지 설명하지 못한다. 구역 자체의 검증 표시와 근거를 제공하고, 구성 노드의 검증 상태와 구분해야 한다.

## 최초 검토에서 통과한 범위와 검증 공백

- 공통 모델에 HTTP·서버·DB 필수 필드가 없고 렌더러에 프로젝트 유형별 분기가 없다.
- 픽스처 11개와 실제 비웹 저장소 3유형·2개 언어를 확보했다. 합성 자료도 구분되어 있어 S0.3의 구성 기준에 맞는다.
- `npm test`: 23개 통과. `npm run test:browser`: 40개 통과.
- 브라우저 테스트에 사용한 HTML 11개가 현재 렌더러로 조립한 결과와 동일함을 확인했다.
- 에이전트·복합·프레임워크·데이터 사례의 상세 보기에서도 다른 노드를 관통하는 관계선이 없는지 추가 확인했다.
- 표준 픽스처 11개 모두 `actions`와 `stateTransitions`가 비어 있다. 세부 동작은 별도 검토 입력에서 표시됨을 확인했지만, 기존 테스트에는 상태 전이의 조건 누락을 잡는 사례가 없다.
- 기존 스냅샷 테스트는 해시를 직접 바꾼 비교를 검사한다. 실제 파일 변경 → 위치 검증 실패 → 이전 짝 페이지 연결이라는 조합은 검사하지 않는다.
- 지도 픽스처의 구역은 확인된 상태만 사용하므로 구역의 추정·미확인 표시 누락도 기존 테스트로 발견되지 않았다.

최초 검토 당시의 재현용 페이지는 Git에서 제외되는 `build/review/transition.html`과 `build/review/uncertain-region.html`에 생성했다. 이후 수정은 위 표와 회귀 테스트에 반영했으며, 최신 표준 예제는 `npm run fixtures`로 생성한다.

M1의 저장소 탐색 스킬, M1.5의 골든셋과 사람 검토, 후속 규칙·지도 탐색은 아직 개발 전이다. 이번 판정은 해당 후속 범위의 완료 여부와 별개다.

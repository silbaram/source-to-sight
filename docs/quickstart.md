# 사용자 퀵스타터

Source to Sight로 실제 프로젝트를 읽고, **프로젝트 지도 → 기능의 동작 → 규칙과 예외**를 설명하는 HTML을 만들어 봅니다. 아래 명령은 터미널에서, `$codebase-atlas` 등으로 시작하는 요청은 에이전트 대화창에서 입력합니다.

## 1. 준비하기

- 로컬 파일 읽기와 명령 실행, Agent Skills를 지원하는 코딩 에이전트
- 분석할 프로젝트의 로컬 소스
- Git, Node.js와 npm/npx, Python 3.10 이상과 pip·venv
- 결과 HTML을 열 브라우저

설치에는 인터넷 연결이 필요합니다. 생성 과정은 사용하는 에이전트의 연결 환경을 따르며, 완성된 HTML은 오프라인에서 열 수 있습니다. 소스를 설명하기 위해 대상 프로젝트의 서버를 실행하거나 의존성을 모두 설치할 필요는 없습니다.

아래 터미널 예시는 Bash 기준입니다. Windows에서는 WSL에서 같은 순서로 실행할 수 있습니다.

## 2. 스킬 설치하기

터미널에서 GitHub 저장소의 모든 스킬을 직접 설치합니다.

```bash
npx skills add silbaram/source-to-sight --global --skill '*'
```

설치 화면에서 사용할 에이전트를 선택합니다. `--global`은 여러 프로젝트에서 사용할 수 있도록 사용자 범위에 설치하며, `--skill '*'`는 저장소의 모든 스킬을 선택합니다. GitHub 직접 설치와 스킬 선택 옵션은 [Skills CLI 공식 안내](https://github.com/vercel-labs/skills#source-formats)를 따릅니다.

다음 단계에서 사용할 `S2S_SOURCE`는 설치된 `skills/` 폴더의 상위 경로입니다. 기본 Symlink 방식의 전역 설치는 `~/.agents/skills/`에 공통 사본을 두므로 아래처럼 설정합니다([설치 경로 구현](https://github.com/vercel-labs/skills/blob/main/src/installer.ts)). Copy 방식이나 다른 설치 경로를 사용했다면 설치 화면에 표시된 실제 경로에 맞춥니다. `$S2S_SOURCE/skills/` 아래에 `code-flow`와 `codebase-atlas`가 있어야 합니다.

```bash
S2S_SOURCE="$HOME/.agents"
```

| 만들 결과 | 필요한 스킬 |
| --- | --- |
| 한 기능의 동작 설명 | `code-flow` |
| 프로젝트 지도와 상세 동작 | `codebase-atlas` + `code-flow` |
| 동작과 연결된 규칙·이유·예외 | `code-flow` + `visual-primer` |
| OAuth 같은 일반 개념 설명 | `visual-primer` |

처음에는 위 명령으로 모든 스킬을 함께 설치하면 모든 흐름을 사용할 수 있습니다. 수동 설치 시에도 각 스킬의 `SKILL.md`뿐 아니라 스크립트·템플릿·참고자료·라이선스를 포함한 폴더 전체를 복사해야 합니다.

## 3. 생성 도구 준비하기

같은 터미널에서 Python 환경을 준비합니다. 이 환경은 소스 기반 지도·동작·규칙 HTML 생성에 사용합니다.

```bash
python3 -m venv "$S2S_SOURCE/.venv"
"$S2S_SOURCE/.venv/bin/python" -m pip install -r "$S2S_SOURCE/skills/code-flow/scripts/requirements.txt"
"$S2S_SOURCE/.venv/bin/python" "$S2S_SOURCE/skills/code-flow/scripts/author.py" doctor
"$S2S_SOURCE/.venv/bin/python" "$S2S_SOURCE/skills/codebase-atlas/scripts/atlas.py" --code-flow-root "$S2S_SOURCE/skills/code-flow" doctor
```

`doctor`는 로컬 생성 도구와 필수 자원을 확인합니다. 설치된 사본에서도 문제가 나면 에이전트에 실제 설치 경로의 `doctor`를 실행해 달라고 요청합니다.

설치 후 분석할 프로젝트를 에이전트에서 열고 새 대화를 시작합니다. 에이전트가 사용할 Python을 찾도록 다음 요청에 **실제 절대 경로**를 전달합니다. 새 대화에는 터미널의 `S2S_SOURCE` 변수가 자동으로 전달되지 않습니다.

```text
Source to Sight 스킬 세 개가 설치되어 있는지 확인해줘.
생성 명령은 /실제/경로/source-to-sight/.venv/bin/python 으로 실행해줘.
```

## 4. 첫 프로젝트 지도 만들기

분석할 프로젝트를 연 대화창에 다음 요청을 입력합니다. 결과 경로는 대상 프로젝트 기준입니다.

```text
$codebase-atlas 현재 프로젝트의 목적, 주요 책임, 대표 기능을 처음 보는 사람이 이해하도록 한국어로 설명해줘.
결과는 build/source-to-sight/project.html에 저장해줘.
우선 프로젝트 지도만 만들고, 확인하지 못한 범위도 표시해줘.
```

에이전트가 소스와 문서를 읽고 근거를 정리한 뒤 HTML 링크를 제공합니다. 링크를 열거나 파일 탐색기에서 `project.html`을 브라우저로 엽니다. GitHub의 HTML 파일 화면에서는 대화형 기능을 직접 사용할 수 없으므로 파일을 내려받아 엽니다.

지도에서 프로젝트 목적을 읽고, 책임 구역과 구성 요소를 눌러 설명과 근거 위치를 확인합니다. 검색·확대·이동·다크모드를 사용할 수 있습니다. 확인한 책임에 따라 그림의 크기가 달라지며, 작은 유틸리티는 노드 하나로 설명될 수도 있습니다.

## 5. 관심 있는 기능의 상세 설명 열기

지도에서 주요 기능을 선택합니다. 아직 상세 페이지가 없다면 **생성 명령 복사**를 눌러 에이전트 대화창에 붙여넣고 다음 내용을 덧붙입니다.

```text
이 기능의 동작 설명을 생성하고 기존 build/source-to-sight/project.html도 다시 생성해줘.
지도에서 상세로 이동하고 다시 지도로 돌아올 수 있게 연결해줘.
내부 작성 데이터는 로컬 작업 폴더에 보관해줘.
```

완료 후 브라우저에서 지도를 다시 엽니다. **동작 설명**으로 이동하면 기능의 처리 흐름과 근거를 볼 수 있습니다. 순서가 있는 시나리오는 **흐름 따라가기**에서 자동재생·배속·단계 선택을 사용할 수 있습니다. 순서가 없는 구성에는 재생기가 나타나지 않을 수 있습니다.

브라우저의 생성 명령 복사 버튼은 요청을 복사합니다. 실제 분석과 HTML 생성은 에이전트에 요청을 전달한 뒤 진행됩니다.

## 6. 규칙과 예외까지 설명하기

같은 대화에서 방금 만든 기능을 지정합니다.

```text
$code-flow 방금 지도에 연결한 기능의 조건, 결과, 이유, 예외를 --explain으로 설명해줘.
기존 기능의 대상과 범위를 유지하고, 지도·동작·규칙 페이지를 서로 연결해줘.
결과는 기존 build/source-to-sight/ 아래에 저장해줘.
```

동작 페이지에서 **규칙과 이유**로 이동해 조건별 결과와 예외를 비교합니다. 지도 없이 한 기능만 설명할 때도 `$code-flow`에 구체적인 함수·명령·생명주기를 지정하면 됩니다.

| 프로젝트 | 상세 요청 예시 |
| --- | --- |
| AI 에이전트 | 도구 호출 결과를 기록하고 반복을 종료하는 조건을 설명해줘. |
| 유틸리티 | 이 변환 함수의 입력 검사와 변환 과정을 설명해줘. |
| 라이브러리 | 캐시 항목 제거와 콜백 호출 조건을 설명해줘. |
| 프레임워크 | 플러그인 등록과 훅 실행 과정을 설명해줘. |
| 이벤트 시스템 | 이벤트 수신자를 선택하고 전달하는 과정을 설명해줘. |
| REST API | 이 엔드포인트의 입력 검증부터 응답·오류 처리까지 설명해줘. |

실제 프로젝트의 함수명·파일 경로·엔드포인트를 함께 적으면 설명할 범위를 더 정확히 정할 수 있습니다.

## 7. 결과 확인·공유·갱신하기

- **내용 확인:** 목적과 주요 흐름이 실제 코드와 맞는지, 실패 조건과 **설명 범위와 한계**를 확인합니다. 소스 근거 확인과 실제 실행 관찰은 구분되며, 이 설명만으로 실행 테스트를 완료한 것은 아닙니다.
- **공유:** 연결된 HTML 파일을 폴더 구조 그대로 함께 전달합니다. 각 HTML의 화면 자원은 자체 포함되어 있지만 다른 상세 페이지로 이동하려면 해당 파일도 필요합니다.
- **작성 데이터:** 내부 JSON에는 근거 앵커가 들어갈 수 있습니다. 로컬에 보관하고, 공유할 때는 생성된 HTML과 표시되는 경로·식별자를 확인합니다.
- **소스 변경:** 에이전트에 최신 소스를 다시 읽어 기존 설명과 연결 페이지를 재생성해 달라고 요청합니다. HTML은 소스 변경을 자동 반영하지 않습니다.

## 자주 막히는 부분

| 증상 | 확인할 내용 |
| --- | --- |
| 스킬이 보이지 않음 | 설치 시 사용할 에이전트를 선택했는지 확인하고 새 대화를 시작합니다. |
| `jsonschema`가 없다는 오류 | 에이전트가 3단계에서 준비한 Python 경로를 사용하는지 확인합니다. |
| 지도 생성 도구를 찾지 못함 | `codebase-atlas`와 `code-flow`가 모두 설치되어 있는지 확인합니다. |
| 규칙 페이지를 만들지 못함 | 같은 구현 버전의 `visual-primer`도 설치하고 동작 범위를 지정합니다. |
| 상세 링크 대신 생성 요청이 표시됨 | 복사한 요청을 에이전트에 전달하고 상세와 지도를 함께 다시 생성합니다. |
| 다른 프로젝트의 파일을 덮어쓸 수 없다는 오류 | 새 출력 폴더를 지정하고 올바른 프로젝트를 열었는지 확인합니다. |

화면 탐색은 [프로젝트 지도 사용 안내](project-maps.md), 파일 구분은 [배포 파일 기준](distribution.md)에서 더 확인할 수 있습니다.

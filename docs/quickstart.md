# 처음 사용하는 사람을 위한 퀵스타터

한국어 | [English](quickstart.en.md)

이 문서를 따라 하면 **내 프로젝트를 설명하는 HTML 파일을 만들고 브라우저에서 열 수 있습니다.** 프로젝트 맵에서 기능·상세 흐름을 거쳐, 핵심 비즈니스 로직을 큰 그림으로 이해하는 순서입니다. 먼저 지도 하나를 만들고 필요한 상세만 추가합니다.

Source to Sight는 코딩 에이전트가 사용하는 스킬 모음입니다. 사용자가 요청하면 에이전트가 실제 소스를 읽고 설명을 작성하며, 함께 설치되는 도구가 데이터를 검사하고 HTML을 만듭니다. 별도의 웹 서비스를 실행하는 제품은 아닙니다.

처음에는 1~4단계까지만 진행하세요. 5~6단계는 첫 결과를 확인한 뒤 선택하면 됩니다.

## 먼저 구분하기: 어디에 입력하나요?

| 장소 | 여기서 할 일 |
| --- | --- |
| 터미널 / Windows PowerShell | 버전 확인과 `npx skills ...` 설치 명령 실행 |
| 코딩 에이전트 대화창 | `$codebase-atlas`, `$code-flow` 등으로 시작하는 설명 요청 입력 |
| 웹 브라우저 | 생성된 `.html` 파일 열기와 화면 탐색 |

`$code-flow`는 터미널 명령이 아닙니다. 이 문서의 **에이전트 대화창** 예시는 사용 중인 코딩 에이전트에 붙여넣으세요. 로컬 파일 접근 기능이 없는 일반 채팅만으로는 프로젝트를 읽을 수 없습니다.

## 1. 필요한 도구와 프로젝트 준비하기

입력 위치: 터미널. Windows는 PowerShell, macOS·Linux는 터미널 앱이나 편집기의 터미널을 사용합니다. WSL은 필수가 아닙니다.

다음 항목을 준비합니다. 이미 설치되어 있다면 다시 설치하지 않아도 됩니다.

- 로컬 폴더 읽기, 명령 실행, Agent Skills를 지원하는 코딩 에이전트: 설치와 로그인을 마쳐 둡니다. 호스트 지원 여부는 [Skills CLI의 지원 목록](https://github.com/vercel-labs/skills#supported-agents)에서 확인합니다.
- [Git](https://git-scm.com/install/): 스킬과 원격 저장소를 가져오는 데 사용합니다.
- [Node.js](https://nodejs.org/en/download): 처음 설치한다면 지원 중인 LTS를 선택합니다. 현재 [Skills CLI의 최소 요구 버전](https://github.com/vercel-labs/skills/blob/main/package.json)은 **22.20.0**이며, npm/npx도 사용할 수 있어야 합니다.
- [Python 3.10 이상](https://www.python.org/downloads/): 소스 기반 HTML 생성에 사용합니다. 별도의 Python 패키지 설치, `pip`, 가상환경 준비는 필요하지 않습니다.
- 설명할 프로젝트의 로컬 소스 폴더와 HTML을 열 브라우저.

먼저 다음 명령을 한 줄씩 실행합니다.

```sh
git --version
node --version
npm --version
npx --version
```

PowerShell에서 `npm.ps1` 또는 `npx.ps1` 차단 오류가 나오면 각각 `npm.cmd --version`, `npx.cmd --version`으로 확인합니다. npm은 Windows용 [npm.cmd](https://github.com/npm/cli/blob/latest/bin/npm.cmd)와 [npx.cmd](https://github.com/npm/cli/blob/latest/bin/npx.cmd)를 제공합니다. 이후 이 문서의 `npx` 명령도 `npx.cmd`로 바꿔 실행할 수 있습니다.

Python은 운영체제에 맞는 명령을 실행합니다.

macOS·Linux:

```sh
python3 --version
```

Windows PowerShell:

```powershell
python --version
```

Windows에서 `python`을 찾지 못하고 Python 런처가 설치되어 있다면 `py --version`으로 확인할 수 있습니다. 이후 에이전트에도 실제로 동작한 명령을 알려주세요.

**완료 기준:** 각 명령이 버전을 출력하고, Node.js는 22.20.0 이상, Python은 3.10 이상입니다. 예를 들어 Python 3.9는 업그레이드가 필요합니다. 명령을 찾지 못하면 위 공식 안내로 설치한 뒤 터미널과 에이전트를 다시 엽니다.

설명할 소스가 이미 컴퓨터에 있다면 그 폴더를 사용합니다. GitHub에만 있다면 먼저 내려받아 압축을 풀거나 Git으로 복제해 로컬 폴더를 준비합니다. **Source to Sight 저장소를 직접 복제할 필요는 없습니다.** 다음 단계에서 스킬을 설치할 수 있습니다.

설치에는 인터넷 연결이 필요합니다. 분석 중 연결과 데이터 처리는 사용하는 에이전트의 설정을 따르므로, 접근 권한과 조직의 소스 이용 정책을 확인하세요. 대상 프로젝트의 서버를 실행하거나 프로젝트의 모든 의존성을 설치할 필요는 없습니다.

## 2. 스킬 설치하기

입력 위치: 터미널. 아래 한 줄은 Bash와 PowerShell에서 모두 사용할 수 있습니다.

```sh
npx skills add silbaram/source-to-sight --global --skill '*'
```

1. 처음 실행해 `skills` 패키지 실행 확인이 나오면 패키지 이름을 확인하고 진행합니다.
2. 에이전트 선택 화면이 나오면 **실제로 사용하는 에이전트**를 선택합니다. 선택 키와 확인 키는 화면 안내를 따릅니다. 자동 선택됐다면 설치 요약의 대상이 맞는지 확인합니다.
3. 설치 방식 선택 화면이 나오면 기본 방식을 사용합니다. 심볼릭 링크 오류가 나면 아래 문제 해결의 `--copy` 방법을 사용합니다.
4. 설치가 끝날 때까지 기다린 뒤, 설치 요약에서 스킬 이름과 대상 에이전트를 확인합니다.

`--global`은 여러 프로젝트에서 쓸 수 있는 사용자 범위 설치이고, `--skill '*'`는 이 저장소의 스킬 전체 선택입니다. 설치 옵션은 [Skills CLI 공식 안내](https://github.com/vercel-labs/skills#options)를 따릅니다.

설치된 목록도 확인합니다.

```sh
npx skills ls -g
```

**완료 기준:** 목록에 `code-flow`, `codebase-atlas`, `visual-primer`가 있고 사용할 에이전트에 연결되어 있습니다. 목록 확인 방식은 [CLI 구현](https://github.com/vercel-labs/skills/blob/main/src/list.ts)을 기준으로 합니다.

이후에는 스킬 폴더를 수동으로 옮기거나 Python 패키지를 추가로 설치하지 않습니다. 수동 복사가 필요한 환경이라면 `SKILL.md`만 복사하지 말고 스크립트·템플릿·참고자료·벤더 파일·라이선스를 포함한 스킬 폴더 전체를 보존합니다.

## 3. 대상 프로젝트를 열고 실행 준비 확인하기

입력 위치: 코딩 에이전트 대화창.

1. 에이전트에서 **설명할 프로젝트의 소스 폴더**를 엽니다. Source to Sight가 설치된 폴더가 아닙니다.
2. 설치된 스킬을 새로 인식하도록 새 대화를 시작합니다.
3. 다음 요청을 복사해 보냅니다.

```text
Source to Sight를 처음 사용하려고 해. 아직 HTML을 만들지 말고 실행 준비만 확인해줘.

1. 현재 열린 프로젝트의 루트 경로를 알려줘.
2. 설치된 code-flow, codebase-atlas, visual-primer의 실제 경로와 사용 가능 여부를 확인해줘.
3. Python 3.10 이상인 실행 명령을 찾아서 버전과 실행 경로를 알려줘.
4. 그 Python으로 설치된 author.py doctor와 atlas.py doctor를 실행해줘.
   code-flow가 별도 위치에 있으면 atlas.py에 실제 --code-flow-root를 전달해줘.

소스 코드나 설정은 수정하지 말고, 준비가 안 된 항목은 오류와 필요한 조치만 알려줘.
```

1단계에서 `python` 대신 `py` 등으로 확인했다면 요청 끝에 그 사실을 덧붙입니다. 에이전트가 로컬 파일 읽기나 위 점검 명령의 실행 승인을 요청하면 대상과 명령을 확인한 뒤 승인합니다.

`doctor`는 생성 도구와 설치 자원이 있는지 확인하는 점검 명령입니다. 프로젝트 분석이나 테스트를 대신하지 않습니다.

**완료 기준:** 프로젝트 경로가 맞고, 세 스킬이 확인되며 두 `doctor` 명령이 오류 없이 끝납니다. 스킬을 찾지 못하면 아래 문제 해결부터 확인하고, 준비가 끝난 뒤 다음 단계로 넘어갑니다.

## 4. 첫 프로젝트 지도를 만들고 열기

입력 위치: 3단계에서 준비를 확인한 같은 에이전트 대화창.

```text
$codebase-atlas 현재 프로젝트를 처음 보는 사람이 이해할 수 있도록 한국어 프로젝트 지도를 만들어줘.
프로젝트의 목적, 주요 책임, 구성 요소의 관계, 대표 기능을 실제 소스에 근거해 설명해줘.
우선 지도만 만들고 상세 기능 페이지는 아직 생성하지 마.
확인한 범위와 확인하지 못한 부분을 구분해줘.

HTML은 프로젝트 루트 기준 build/source-to-sight/project.html에 저장해줘.
재생성에 필요한 내부 작성 데이터는 work/source-to-sight/에 따로 보관해줘.
소스 코드와 설정 파일은 수정하지 마.
완료되면 HTML의 절대 경로와 링크, 내부 작성 데이터의 위치를 알려줘.
```

`build/source-to-sight/`는 이 안내에서 정한 **결과 폴더**이고, `work/source-to-sight/`는 **에이전트의 내부 작성 데이터 폴더**입니다. 없으면 생성 과정에서 만듭니다. 파일을 직접 작성할 필요는 없습니다. 프로젝트에 별도의 결과물 저장 규칙이 있으면 요청의 두 경로를 그 규칙에 맞게 바꾸세요.

에이전트가 소스를 읽고 파일을 생성할 때까지 기다립니다. 여러 패키지가 있어 범위를 물으면 처음 확인할 패키지 하나를 지정하세요. 기존 출력이 다른 프로젝트·대상·언어의 파일이면 덮어쓰지 말고 새 출력 경로를 지정합니다.

완료되면 다음 순서로 확인합니다.

1. 에이전트가 준 HTML 링크를 엽니다. 링크가 동작하지 않으면 파일 탐색기에서 `build/source-to-sight/project.html`을 찾아 브라우저로 엽니다.
2. 프로젝트 목적과 설명 범위를 읽습니다.
3. 구성 요소나 주요 기능을 눌러 역할과 근거 위치를 확인합니다.
4. 확인하지 못한 내용과 **설명 범위와 한계**도 읽습니다.

GitHub의 HTML 파일 화면은 완성된 대화형 페이지가 아닙니다. 원격 파일이라면 내려받아 로컬 브라우저로 엽니다. 결과를 보는 데 Node.js, Python, 웹 서버는 필요하지 않으며, 지도 조작에는 브라우저의 JavaScript가 필요합니다.

**완료 기준:** `project.html`이 브라우저에서 열리고 목적·구성·근거를 탐색할 수 있습니다. 작은 프로젝트는 노드 하나로 표현될 수도 있습니다. 여기까지 하면 첫 사용은 완료입니다.

## 5. 선택 사항: 한 기능의 동작 설명 추가하기

입력 위치: 먼저 브라우저, 다음으로 같은 에이전트 대화창.

1. 지도에서 관심 있는 **주요 기능** 하나를 선택합니다.
2. 이미 **동작 설명** 링크가 있으면 열어봅니다.
3. **생성 명령 복사**가 나오면 눌러서 요청을 복사합니다.
4. 복사한 요청을 에이전트에 붙여넣고 다음 내용을 덧붙여 함께 보냅니다.

```text
복사한 요청의 대상, 범위, 출력 경로를 유지해서 이 기능의 동작 설명을 만들어줘.
내부 작성 데이터는 work/source-to-sight/에 보관해줘.
이 기능만 추가하고, 기존 build/source-to-sight/project.html도 다시 생성해서
지도에서 상세로 이동하고 상세에서 같은 지도로 돌아올 수 있게 연결해줘.
완료되면 생성한 HTML 파일들의 경로를 알려줘.
```

처음 요청에서 결과 폴더를 바꿨다면 여기에도 같은 경로를 사용합니다. 복사가 안 되면 지도에 나온 기능 이름을 에이전트에 전달하고, 그 기능의 대상과 범위를 확인한 뒤 생성해 달라고 요청하세요.

**완료 기준:** 생성이 끝난 뒤 지도를 다시 열거나 새로고침하면 해당 기능의 상세 페이지로 이동하고 돌아올 수 있습니다. 실행 순서가 있는 동작은 **흐름 따라가기**로 살펴볼 수 있고, 순서가 없는 관계도에는 재생기가 없을 수 있습니다.

브라우저의 복사 버튼은 요청만 복사합니다. 버튼을 누르는 것만으로 분석이나 HTML 생성이 시작되지는 않습니다.

## 6. 선택 사항: 조건·이유·예외 설명 추가하기

입력 위치: 5단계와 같은 에이전트 대화창.

이 단계의 결과는 [OAuth 예시](../assets/oauth-visual-primer-example.html)처럼 그림이 설명의 중심인 페이지입니다. 핵심 판단을 큰 그림으로 보여주고, 조건 선택이나 단계별 조작이 이해에 도움이 되면 포함합니다. 모든 비즈니스 로직을 같은 카드나 흐름도로 표현하지 않습니다.

```text
$code-flow --explain 방금 지도에 연결한 기능의 조건, 결과, 이유, 예외를 한국어로 설명해줘.
핵심 비즈니스 로직을 처음 보는 사람도 이해하도록 visual-primer의 맞춤형 그림 설명으로 만들어줘.
큰 그림과 짧은 설명을 중심으로 구성하고, 필요한 경우 실제 조건·분기를 살펴보는 조작을 넣어줘.
기존 동작 설명의 대상과 범위를 유지하고 실제 소스를 다시 확인해줘.
내부 작성 데이터는 work/source-to-sight/에 보관해줘.
지도·동작·규칙 페이지를 함께 갱신해서 서로 이동할 수 있게 연결해줘.
결과는 기존 build/source-to-sight/ 아래에 저장하고 HTML 경로를 알려줘.
```

`--explain`은 여기서는 **스킬 요청의 표시**입니다. 터미널에서 그대로 실행하지 않습니다. 이 작업에는 `code-flow`와 `visual-primer`가 함께 필요하며, 2단계에서 모두 설치했습니다.

**완료 기준:** 지도 → 동작 설명 → **규칙과 이유** 순서로 들어가 핵심 비즈니스 로직을 그림으로 이해하고, 근거를 펼쳐 정확한 조건·이유·예외를 확인한 뒤 동작 설명과 같은 지도로 돌아올 수 있습니다. 근거가 부족한 그림은 추측으로 채우지 않고 검토 필요 안내로 남습니다.

원하는 그림 스타일의 HTML이 있다면 실제 파일 경로를 요청에 덧붙이세요. 예시 파일은 이 저장소의 `assets/`에 있으며, 스킬만 설치한 다른 프로젝트에 자동 복사되지는 않습니다. 참고 HTML이 없어도 맞춤형 그림 설명이 기본입니다.

## 지도 없이 바로 시작하거나 영어로 만들기

프로젝트 전체보다 한 기능이 궁금하면 3단계의 준비 확인 후 바로 `$code-flow`를 사용할 수 있습니다. 아래 `대상 함수명`은 프로젝트의 실제 함수명이나 파일 경로로 바꿉니다.

```text
$code-flow 대상 함수명의 입력, 처리 과정, 반환 결과와 오류 처리를 소스에 근거해 한국어로 설명해줘.
HTML은 build/source-to-sight/에, 내부 작성 데이터는 work/source-to-sight/에 보관하고 경로를 알려줘.
```

일반 개념 그림은 소스 기반 지도·동작 설명과 별도의 흐름입니다.

```text
$visual-primer OAuth가 무엇인지 처음 배우는 사람에게 그림 중심의 한국어 HTML로 설명해줘.
build/source-to-sight/oauth.html에 저장해줘.
```

영어 결과를 원하면 출력 언어를 명시합니다.

```text
$codebase-atlas Explain this project's purpose, responsibilities, and representative capabilities in English.
Generate only the project map at build/source-to-sight/project.en.html.
Keep internal authoring data separately under work/source-to-sight/en/ and report all file paths.
Show the reviewed scope and anything that could not be verified. Do not modify source code or configuration.
```

한국어와 영어는 설명뿐 아니라 화면 조작 안내도 지원합니다. 두 언어가 필요하면 각각 요청하고 파일 경로를 나눕니다. 같은 파일을 다른 언어로 덮어쓰지 않으며, 관련 페이지도 같은 언어로 맞춥니다. 영어로 처음부터 진행하려면 [English quickstart](quickstart.en.md)를 사용하세요.

## 만든 파일 보관·공유·다시 생성하기

| 파일 / 폴더 | 용도와 주의점 |
| --- | --- |
| `build/source-to-sight/`의 HTML | 브라우저에서 보는 결과. 연결된 HTML을 함께 공유해야 페이지 이동이 유지됩니다. |
| `work/source-to-sight/`의 내부 JSON | 에이전트가 근거를 검토하고 다시 생성할 때 쓰는 데이터 파일. 근거 확인용 원문이 있을 수 있어 공유용이 아닙니다. |
| 선택적으로 생성되는 render JSON | 화면 표시용 데이터. 내부 작성 JSON을 대신하지 않으며, HTML만 볼 때는 필수가 아닙니다. |

파일은 UTF-8로 읽고 씁니다. 공유할 때는 HTML에 표시되거나 포함된 프로젝트명·경로·식별자·설명도 검토하세요. 연결된 HTML의 폴더 구조를 유지해 묶어서 전달하면 받는 사람은 내려받고 압축을 푼 뒤 `project.html`을 열 수 있습니다. 내부 작성 데이터는 공유 묶음에서 제외합니다.

소스가 바뀌어도 HTML이 자동 갱신되지는 않습니다. 기존 파일과 내부 작성 데이터가 있는 프로젝트에서 다음처럼 요청합니다.

```text
build/source-to-sight/project.html과 연결된 기존 설명을 최신 소스 기준으로 다시 검토하고 생성해줘.
work/source-to-sight/의 내부 작성 데이터를 참고하되 변경된 근거와 설명을 다시 확인해줘.
기존 대상·범위·언어를 유지하고, 이미 생성한 페이지의 링크도 갱신해줘.
아직 만들지 않은 다른 기능의 상세 페이지는 생성하지 마.
```

Source to Sight 자체를 업데이트하려면 **2단계의 설치 명령을 다시 실행**하고, 새 대화에서 **3단계의 준비 확인**을 반복합니다. 설치 사본을 직접 수정했다면 먼저 별도로 보관하세요. 스킬 업데이트만으로 기존 HTML이 바뀌지는 않습니다.

## 자주 막히는 부분

| 증상 | 먼저 할 일 |
| --- | --- |
| `git`, `node`, `npm`, `npx`를 찾지 못함 | 1단계의 해당 도구를 설치하고 터미널과 에이전트를 다시 엽니다. |
| `EBADENGINE` 또는 Node 버전 오류 | Node.js를 지원 중인 LTS로 업데이트하고 현재 CLI의 요구 버전을 확인합니다. |
| Windows에서 `npx.ps1` 실행이 차단됨 | npm이 제공하는 [npx.cmd](https://github.com/npm/cli/blob/latest/bin/npx.cmd)로 아래 명령을 실행합니다. 보안 정책을 일괄 해제할 필요는 없습니다. |
| 심볼릭 링크 생성 오류 | 아래 `--copy` 설치 명령을 사용하고 같은 에이전트를 선택합니다. |
| 설치했는데 스킬이 안 보임 | `npx skills ls -g`에서 이름과 연결된 에이전트를 확인하고, 대상 프로젝트에서 새 대화를 시작합니다. `$` 호출이 인식되지 않으면 호스트의 스킬 선택 기능으로 해당 이름을 선택합니다. |
| `jsonschema`를 설치하라는 오류나 오래된 안내가 나옴 | 이전 스킬 사본을 실행 중일 수 있습니다. 2단계로 업데이트하고 3단계에서 실제 로드한 경로를 확인합니다. |
| HTML이 생성되지 않음 | 에이전트에 오류 전문, Python 실행 경로·버전, 설치 경로의 두 `doctor` 결과를 확인해 달라고 요청합니다. |
| HTML을 못 찾음 | 에이전트에 결과의 절대 경로를 요청합니다. 설치 폴더가 아니라 대상 프로젝트의 결과 폴더에서 찾습니다. |
| 상세 링크 대신 생성 요청만 표시됨 | 5단계의 요청을 보내 상세를 생성하고 지도를 다시 생성한 뒤 새로고침합니다. |
| 규칙 페이지가 없음 | 6단계를 요청했는지와 `visual-primer` 설치 여부를 확인합니다. 서로 다른 시점의 스킬을 섞어 설치했다면 2단계로 세 스킬을 함께 업데이트합니다. |
| 다른 프로젝트·대상·언어의 파일이라는 오류 | 기존 파일을 지우거나 검사를 우회하지 말고 새 출력 경로를 지정합니다. |
| 예전 JSON에서 `/snapshot/generatedAt` 오류 | 아래 호환성 안내를 따릅니다. |

Windows의 `npx.ps1` 차단 시, PowerShell에서:

```powershell
npx.cmd skills add silbaram/source-to-sight --global --skill '*'
```

심볼릭 링크 오류 시, 터미널에서:

```sh
npx skills add silbaram/source-to-sight --global --skill '*' --copy
```

두 문제가 함께 있으면 `npx.cmd` 명령에 `--copy`를 덧붙입니다. [복사 설치 옵션](https://github.com/vercel-labs/skills#installation-methods)은 스킬 파일을 복사하는 방식이며 WSL 설치나 전역 보안 설정 변경을 요구하지 않습니다.

### 기존 JSON 재생성 시 호환성 변경

검증기가 내장된 작성 도구 0.7.0부터 내부 JSON의 `snapshot.generatedAt`을 항상 RFC 3339 형식으로 검사합니다. 이전 환경에서 통과했던 잘못된 날짜·시간이나 문자열 끝의 개행도 이제 거부하므로, 과거 JSON을 다시 `build`할 때 검증 오류가 날 수 있습니다.

원래 생성 시각과 시간대를 확인해 `2026-09-07T12:00:00+09:00` 또는 UTC의 `2026-09-07T03:00:00Z`처럼 교정하고, 문자열 끝의 개행을 제거한 뒤 UTF-8로 저장해 다시 실행합니다. 검증을 우회하거나 현재 시각으로 임의 변경하지 않습니다. 에이전트에 이 오류와 내부 JSON 경로를 전달해 교정을 요청해도 됩니다.
